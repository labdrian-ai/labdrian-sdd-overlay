# review-chain-integration-base: the review chain is done at a range that starts in the integration base

Objective: `review check --base`/`--onto` and `review anchor --merge` clear a branch that was made on a main merge commit and later merged main in (known error memorycard #6179). Branch `fix/review-chain-integration-base` from `origin/main` `39574646`; Tier 3 (inception-pipeline rule 2: single surface, no new architecture, schema or integration); one PR, merged after green CI, then CI of PR #789 re-run.
Test runner: `cd engine && GOTOOLCHAIN=go1.26.1 TMPDIR=/home/labdrian/.cache go test ./...`.

## Specs

- **S1 (where the chain is done).** The owner's fix line (#6179, verbatim): "--onto (and --base) should stop at any commit reachable from the integration branch instead of requiring a review link for it. Commit the fix with a regression test that reproduces this branch shape: a branch made on a main merge commit, then main merged in."
  - `CheckChain` (`engine/review/app/chain.go`) is done at a range whose start is the delivery base, as today, or whose start is an ancestor of the delivery base (Git port `IsAncestor`), subject to S2. The ranges it returns then begin with that range; `Chained.Base` stays the delivery base, so the first range's `base` can differ from the top-level `base`.
  - The rule lives in `CheckChain`, so it holds for all three callers with no change to them: `review check --base` (`engine/cmd/review.go:555`), `review check --onto` (`engine/review/app/onto.go:45`) and `review anchor --merge` (`engine/review/app/landing.go:86`).
  - `IsAncestor` is asked only when the start is not the delivery base, so a chain that reaches the base itself makes the same git calls as today.
  - A git failure of `IsAncestor` refuses the chain with the usual prefix `the chain from <base> to <head>: ` and wraps the cause.
  - Acceptance: on the branch shape of S3 (a), `review check --onto main`, `review check --base main` and `review anchor --merge` clear, where today they fail with "the commit does not declare its risk in a Risk trailer: commit <the main merge commit>".
- **S2 (a range that straddles the base is still refused).** Proposed by the shaper and not yet Decided by the owner (see L2): a range whose start is an ancestor of the base, but whose oldest covered commit is also an ancestor of the base (it passes the base), does not end the chain. The walk goes on as today and is refused as today. The oldest covered commit is the commit on the walk whose first parent is the start: the last commit `insideRange` holds, or the commit the range ends at when its first parent is the start.
  - Acceptance: `TestCheckBaseRefusesAChainThatDoesNotReachTheBase`, subtest "a range that begins before the base" (`engine/cmd/review_check_chain_test.go:183`), passes unchanged.
- **S3 (tests and the words that describe the rule).**
  - (a) Regression test, at the command line over a real repository (`reviewWorld`, `engine/cmd/review_check_chain_test.go`): main gets a merge commit M made with `--no-ff` whose message has no Risk trailer, as a GitHub merge has none; topic is made on M with reviewed commits from M; main moves on past M (a commit and/or a second merge) to T; topic merges main in (merge commit, its review recorded from its first parent) and gets one more reviewed commit. `review check --onto main` and `--base main` exit 0, and the first range starts at M. Before the fix the same test fails with the Risk-trailer refusal naming M.
  - (b) `review anchor --merge HEAD` of a no-ff merge of that topic into main clears the feature (in the same file or `engine/cmd/review_anchor_test.go`).
  - (c) Unit test in `engine/review/app` (fakeGit): `IsAncestor` failing refuses the chain with the prefix and the wrapped cause.
  - (d) `TestCheckOntoClearsTheChainFromWhereTheBranchWasMade` (`review_check_chain_test.go:286`) asserts as setup that `--base main` is refused after main moved on; with S1 it clears (start = fork point, an ancestor of main, and the topic commits are not in main). That setup changes to expect a clear `--base main` whose top-level base is main and whose first range starts at the fork point; the comparison of `--onto main` with `--base <fork point>` stays.
  - (e) Text: the `review check` help (`engine/cmd/usage.go:193-196`), its copy in `README.md:685-693`, the comments of `CheckChain` (`chain.go:25-36`, `17-19`) and of `reportChained`'s caller (`engine/cmd/review.go:498`) say the walk is done at the base or at a range that starts at an ancestor of the base and covers no commit of it, and that the ranges start from that range. `CHANGELOG.md`, `## Unreleased` / `### Fixed`, gets one entry naming the shape, the three verbs and #6179's error text.

  - Steelman: the merge base is only a proxy for "commits the integration branch already has". The chain walks back along the head's first parents, but a branch made on a merge commit of main has its oldest range starting at that merge commit (87f26495). That commit is in main but is not the merge base (ce22eb3f), so the walk steps past the end of the branch and holds a main commit to the Risk-trailer rule. Asking git whether the start is in the base fixes exactly that, and `IsAncestor` already exists on the port (`app.go:144-146`, used by `proposals.go:47`).
  - Rule: done when `start == base`, or when `IsAncestor(start, base)` holds and `IsAncestor(oldest, base)` does not, where `oldest` is the covered commit whose first parent is `start` (S2). `insideRange` returns that commit so no extra walk is needed.
  - Safety argument: let L be the head's first-parent line and B the base. The set of B's ancestors is closed under parents. So if `oldest` is not in it, no newer commit on L is either: all the commits the chain covers are in B..head. Conversely, a commit on L that is older than `start` is an ancestor of `start`, so of B, so it is not in B..head. The chain therefore covers exactly the first-parent commits of B..head, which is what it covers today when it stops at the merge base. The commits between `start` and B are ancestors of B: they are already on the integration branch, and the merge does not deliver them, so this delivery has nothing to review in them. The second-parent sides of merges stay covered by the merge commit's own range, as today.
  - Why S2's guard: without it, a range S..E with B strictly inside it on L (the existing subtest "a range that begins before the base") would clear. Its reviewed diff is diff(S, E), but the delivery is diff(B, E). If a commit between S and B added something that a later commit removed, the reviewer never saw that removal being delivered. The guard keeps that refusal, which is Decided behaviour pinned by that test (own-rdd). It costs a second `IsAncestor` call per range that starts at an ancestor of the base.
  - insideRange: no new stop. Under the done condition no commit it walks is an ancestor of B (closure argument above), so there is nothing to stop at. A range that passes the base is refused whether or not `insideRange` stops. It keeps holding inside commits before the done check, as today.
  - Scope of the stop: all three callers (`--base`, `--onto`, `anchor --merge`), because the rule is in `CheckChain` and #6179 names "--onto (and --base)". Behaviour change: `--base main` after main moved on now clears where it was refused (S3 d). The help said `--onto` exists so the role "does not compute it when the branch moved on"; that stays true.
  - Strongest counter-argument to this design: it diverges from the owner's literal "stop at any commit reachable from the integration branch" (S2 refuses a reachable start when the range straddles the base). It also adds up to two git calls per range. The literal rule is simpler (one call), but it flips a pinned refusal and accepts a reviewed diff that differs from the delivered one. Rejected alternative: changing only `CheckOnto` to pick another base, such as the fork point. `anchor --merge` computes its own merge base (`landing.go:63-70`), and there is no single fork point once main has been merged in. Tradeoff accepted: the extra git calls and an open product question (S2), in exchange for no weakening of an existing refusal.
