# Phase 9 C28: the precision of our review, measured on the 158 findings of C27's 30 runs over R34-R43 by a blind judge, the parent's spot check, and reproduction of every BLOCKER and CRITICAL

Objective: Phase 9 item C28, after C27 (met on recall and cost, L15 of `odd/tasks/phase9-c27-review-recall.md`): label each finding our review returned in C27 T6's 30 runs as real, false or unsure, and compute its precision, with no new review run. Shaping branch `docs/phase9-c28-review-precision` (from main 835dcd3a); task branches `feat/phase9-c28-t<n>`, one PR per task, stacked-to-main, merged in order; one workflow per task, `labdrian workflow open --feature phase9-c28-review-precision --task T<n>`; goal file `odd/goals/phase9-c28-review-precision.json`.
Test runner: `go test` in `engine/` (`engine/shelltest` for the bench scripts), `shellcheck` over the bench scripts; the judging and the spot check are live measurements with no runner (their numbers are evidence in the Log); writer `builder` when a task names one, judge and reproducer `verifier`.

Scope: "de nuestro lado": the findings of our review in the 30 runs of C27 T6 (`RUN=<k> ROWS=recall,hunt tools/review-bench/run-ours.sh R<n>`, k = 1, 2, 3, R34-R43, model `claude-sonnet-5-5`, binary from main 495454cf; C27 L15); no review is run again. What those runs carried, stated precisely: `review launch --runtime claude`, whose prompt is the tool-free preamble `engine/review/claudeprint/preamble.md` with its relaxed first sentence (C27 S4, L11), plus the rows `recall` (the G2 wording, C27 L13) and `hunt`; that runtime never reads the reviewer body (`preamble.md` is the prompt of `--runtime claude` alone, C27 L19), so T8's body change (C27 S8) is not in these runs, and the role chain's reviewer (body, tools and a worktree) is not what is measured. Not in scope: gentle-ai's findings (open, L2); a pass/fail bar and what the result leads to (open, L2); the severity or the causality a finding declares (only whether its claimed failure holds); any change to the reviewer body, the preamble, the rows, the role chain or engine code; the scoring rule of C25 L3. Acceptance: T1-T4 delivered in order; the result entry of S6 in the Log.
- **S2 — The findings, frozen and committed before anything else.** Scope: (a) a script `tools/review-bench/findings.sh` reads `$BENCH/out/ours/run<k>/<id>/summary.json` for k = 1, 2, 3 and each id it is given, and writes one JSON array; the findings live in each summary's `lenses[].findings` (observed, `out/ours/run1/R34/summary.json`), not in `launch-*.json`, which hold only the handoff and a reference to the stored result (observed, `out/ours/run1/R34/launch-recall.json`); (b) its output for R34-R43 is committed as `tools/review-bench/findings/ours-c27.json`, one entry per finding: `{"key","id","run","row","finding","severity","location","claim","proof_refs","evidence_class","causal_disposition","c27_control"}`, where `key` is the first 12 hex digits of the sha256 of `<id>/<run>/<row>/<finding>` (an opaque name that carries no runner, row, run or score, and whose order is a fixed pseudo-random shuffle) and `c27_control` is true when the finding's row, severity and location equal the prefix of the quote of a score-1 or score-0.5 entry of `tools/review-bench/scores/ours-c27.json` for the same id and run (a finding C27 judged to state the seeded defect, so known to be real by its fix); (c) no deduplication: each of the 158 is a finding a delivery must resolve (memory "resolve every review finding"), so precision is per reported finding, and the same defect reported in several runs or rows is judged each time (which also shows the judge's consistency); (d) the freeze precedes any rerun of `run-ours.sh`, since the bench scripts `rm -rf` their output per case (C27 S2). Assumption: each score quote's prefix matches exactly one finding; a quote that matches none or several is named in the Log and its findings get `c27_control: false`. Acceptance: the file holds 158 entries (77 WARNING, 81 SUGGESTION, 0 BLOCKER, 0 CRITICAL, as counted in L2); per id, run and row, its count equals that lens's `n` in the summary; every `key` is distinct; the shell tests of T1.
- **S3 — The blind judge.** The proposal (S1): "un verifier ciego etiqueta cada hallazgo como real, falso o dudoso, citando el código". Scope: (a) *Judge*: the `verifier` role (read-only, `roles/verifier/body.md`), launched by the parent as a sub-agent, one launch per case (10 launches), on a model other than the reviewer's `claude-sonnet-5-5` (assumption: `opus`, the role chain's precedent of a second blind launch on another model). (b) *What it is given*: a directory outside this repository and the bench clone, `~/labdrian-sdd-overlay-worktrees/c28-judge/<id>/`, holding `head/` and `base/` exported with `git -C $BENCH/repo archive` (no `.git`, so no history, fix or later commit is reachable), and `diff.patch` from `git -C $BENCH/repo diff <base> <head>`; and the case's findings as claims, each with only its `key`, `location`, `claim` and `proof_refs`, in `key` order. It is never given the runner, the row, the run, the severity, the evidence class, the causal disposition, the score, the corpus entry or the defect. (c) *The brief* is a template committed as `tools/review-bench/judge-brief.md`, the same for every case: for each claim, read the code at head (and base or the diff when needed) and label it `real` (the failure the claim states happens at head as stated), `false` (it does not happen, or the code shows the claim is wrong) or `unsure` (reading cannot decide), with one code citation `path:line` or `path:start-end` in `head/` or `base/` and a one-sentence reason; and `failure_stated`: false when the claim names no failure (for example a coverage or style remark), true otherwise. The judge writes one file the brief names, outside the repository, `{"labels":[{"key","label","failure_stated","citation","reason"}]}`, one entry per key, none twice; it runs no command that changes a file outside that path. (d) *Pilot and stop*: the first launch is R41 (4 findings); when its file is missing, not that shape, or misses a key, or the verifier answers in its finding-verdict shape instead (`roles/verifier/body.md:9-10`), the parent stops C28 at T3 and reports, and no role body is changed for it. (e) *Failure of one launch*: relaunched once with the same brief; still failing, its keys are recorded `not-judged`, named in the Log and left out of every ratio; no label is invented. (f) The labels of the 10 files are merged into `tools/review-bench/precision/labels-ours-c27.json` unchanged. Acceptance: one label per key of the findings file (158, or the `not-judged` named); every `real` and `false` holds a non-empty citation that names a file present in the export.
- **S4 — Reproduction of every BLOCKER and CRITICAL.** The proposal (S1): "con la reproducción del 2 solo para los BLOCKER y CRITICAL, que es donde un falso positivo cuesta caro". Scope: every finding of severity BLOCKER or CRITICAL is also given to the `verifier` in its existing finding-verdict contract (`roles/verifier/body.md:9-10`: reproduced | not-reproduced | not-run on head and on base, with command and output), over the same exports, after its reading label of S3 is in; its label for the metric is then `real` when reproduced on head, `false` when not-reproduced, `unsure` when not-run, and the reading label is kept beside it. The results go in `tools/review-bench/precision/repro-ours-c27.json`. Evidence: the 158 findings hold 0 BLOCKER and 0 CRITICAL (L2), so this step reproduces nothing on these runs; it is defined so that C29 onward repeats it. Acceptance: the Log says how many findings it applied to; when 0, no repro file is written.
- **S5 — The parent's spot check.** The proposal (S1): "y yo controlo una muestra contra el código". Scope: (a) the sample is the 30 findings with the lowest `key` (19% of 158), fixed by S2's file alone; (b) the parent labels them by the rules of S3 (c), from the same exports, into `tools/review-bench/precision/spot-ours-c27.json` (same entry shape), committed before any judge is launched, so the parent's labels are not anchored on the judge's; the parent is not blind (it knows the runner and the scores), which is stated, not hidden; (c) after T3, the comparison: the agreement count on the sample, and every disagreement with both labels and both citations in the Log; (d) the judge's labels are never edited by the parent: the metric of S6 is the judge's, the parent's labels are evidence beside it; (e) the control: every finding with `c27_control: true` that the judge labels `false` or `unsure` is listed in the Log as a judge error against a known-real finding. Acceptance: 30 entries committed before T3's first launch (commit order); the agreement and control lists in S6's Log entry.
- **S6 — The precision and where it is recorded.** Scope: a script `tools/review-bench/precision.sh` reads the findings, labels and (when present) repro files and prints, overall, per severity, per row (`recall`, `hunt`) and per case: the counts `real`, `false`, `unsure`, `not-judged`; precision `real / (real + false)`; and the bounds `real / judged` (every `unsure` counted false) and `(real + unsure) / judged` (every `unsure` counted real), `judged` being all but `not-judged`; and the same counts split by `failure_stated`. Which of these is "the" precision is not decided here (open, L2). The Log entry of T4 holds that output, the agreement and control of S5, the cost (launches, relaunches, `not-judged`), and no verdict, since the owner set no bar. `tools/review-bench/README.md` says how to repeat it for a later run set. Acceptance: the numbers in the Log equal the script's output; real + false + unsure + not-judged = 158; the shell tests of T4.

  - *Evidence (observed by Grep over `$BENCH/out/ours/run*/R*/summary.json`).* 77 WARNING and 81 SUGGESTION findings, 158 in all, as C27 L15 says; 0 BLOCKER and 0 CRITICAL (the whole `out/ours` tree). Gentle's 30 runs (`out/run<k>/R<n>/summary.json`) hold 31 findings over 16 summaries, for the open decision on judging them.
  - *Steelman.* A reviewer that reports nine times as many findings (C27 L4) wins recall cheaply if half of them are wrong, and every one is a fix before delivery here (`skills/role-chain/SKILL.md:35`). Recall alone cannot tell the difference. A blind judge with code citations is cheap (10 launches), repeatable for C29 onward from committed files and a committed brief, and its weakness, that it measures the judge, is checked twice: by the parent's sample, labeled before the judge runs, and by the findings C27 already proved real by their fix (`c27_control`), a ground truth the judge does not know it is given. The judge uses an existing role and contract with no body change (minimalism, role design principles), and the exports without `.git` make blindness a property of the input rather than a promise of the brief.
  - *Chosen approach.* Freeze first (T1), because a rerun erases the evidence. The parent's sample before the judges (T2), so the comparison is not anchored. The judges, one per case, on another model than the reviewer's, with a pilot that stops the task if the verifier does not follow a reading brief (T3). The metric with both bounds, so no decision on `unsure` is needed to compute it (T4).
  - *Strongest counter-argument.* The judge is the verifier, whose body is written for deterministic reproduction and whose finding-verdict mode fires "for every finding id the prompt lists" (`roles/verifier/body.md:9`); a brief that lists claims to read, not to reproduce, leans on the body's general rules (`:3`, `:8`) and may not be followed, and the label it returns is a model's reading, the very thing S1's option 1 admits ("lo que mide depende del juez"). Blindness is partial: the judge can still reach this repository or the bench clone by path if it wanders, and the parent's sample is not blind at all. One label per finding means duplicates across runs weigh the result toward what the reviewer repeats. And the number measures the tool-free bench configuration, not the role chain's reviewer, which reads a body and a worktree (S1). Answer: the pilot of S3 (d) stops on the first sign the contract does not hold; the two controls give the judge's error rate in the Log; the scope limit is written in S1 so the result is not read as the chain's precision; whether to measure the chain is not designed here.
  - *Tradeoff accepted.* A precision that depends on one model's reading, checked on 30 findings and on the known-real controls, in exchange for about 10 launches instead of 158 reproductions or 158 hand labels, and for repeatability. Per-case batches (all of a case's claims in one launch) save reading the same code ten or more times, at the risk that one claim's label anchors the next; the key order mixes runs and rows to soften it.
  - *Who consumes what changes.* Nothing outside `tools/review-bench/`, `engine/shelltest/review_bench_test.go` and this document: no engine code, role body, generated agent, skill or approval record changes, so no item of the high-risk list applies (`Risk: none` on every task). The new scripts are read by no product command.
  - *Order and sizes.* T1, T2, T3, T4, one PR each, stacked-to-main, merged in order (T1 and T4 both touch the bench README and the shell tests). Forecast in authored changed lines: T1 ~120-220 (plus the generated 158-entry file), T2 ~30-50 (data), T3 ~60-100 (the brief and records, plus the generated labels), T4 ~120-200; ~330-570 in total over 4 commits, none over ~400. Cost forecast: 10 judge launches, at most 10 relaunches, 0 reproductions on these runs; the tokens per launch are not measured (unverified; the exports are one commit's tree and 4-25 claims each).
