# ODD Task — Phase 8: Skill lifecycle and projection

> **Roadmap authority:** [Standalone Platform Master Roadmap](../../openspec/decisions/standalone-platform-roadmap.md), canonical **Phase 8 — Skill lifecycle and projection**: govern candidate → draft outside skills → human approval → `skills/<id>/SKILL.md` → install → manifest sync → runtime projection; test approval, registry/manifest consistency, locks, foreign-file preservation, drift, revisions, report-only retirement. Linked sources: product P3/P8 skill lifecycle acceptance; task aliases `skill-lifecycle`, `skill-package-manager`, `skill-project-scope`, `skill-manifest-gen` (compared, not merged); procedural skill-specific ledgers remain distinct.

## Problem and why

Most of the skill lifecycle already exists in `engine/skills` (add, validate, lint, install, sync-manifest, project-register/revise/retire, an ownership-by-hash lock), and the four aliases are implemented but never reconciled. The gaps are specific: the engine keeps no record of human approval; `skills install` removes the destination directory before copying, so foreign files are not preserved; the registry/manifest dual write has no cross-process lock; no test walks candidate to projection end to end; no typed capability says what skill projection each runtime has. Phase 8 closes those gaps and proves what exists; it does not rebuild the lifecycle.

## Decisions (user, 2026-09-30)

1. **Approval is the only typed governance state.** Candidates and drafts stay in Engram and the contract prose. The engine adds a typed human-approval record bound to the digest of the skill file, and `skills add` for the global tier requires it.
2. **Projection is declared and proven, not rebuilt.** `skills` becomes a typed capability in the Phase 7 model with per-runtime evidence; `skills install` also covers `.agents/skills`; the global tier keeps depending on `labdrian apply`, stated as a limit. No standalone global installer (that is product P8, open and distinct).
3. **`skills install` preserves foreign files** through ownership by hash with the existing lock (`EvaluateOwnership`): it replaces only what it still owns unmodified, and refuses a foreign directory or a hand-edited file with the reason.
4. **Report-only retirement is proven for the project tier only.** The global tier has no detector; a global skill is retired by hand. Declared as a limit.
5. **The four SDD aliases are compared and linked, not archived.** Archiving and spec sync go to the cleanup backlog.
6. **The approval record lives in the repository** next to the skill, created by `labdrian skills approve`, committed with the skill; a `PreToolUse` hook denies the agent running `skills approve` (a speed bump, not a security boundary).

## Engineering defaults (parent; user approved with the design, may overturn)

- **Cross-process exclusion** (`flock`, the Phase 6/7 idiom, bounded wait) around the registry/manifest dual write and around `install`.
- **Grandfathering.** The global skills present at the Phase 8 base have no approval record and are exempt through a fixed, tested baseline list; every new or modified global skill needs a record.
- **Adoption.** A pre-existing install without a lock entry is foreign to `install`; an explicit `skills adopt` step takes ownership. Nothing is adopted silently.
- **Candidate detection is not wired to anything automatic.** It stays a manual procedure, declared as a limit, consistent with "no automatic promotion".
- **New code** imports no `os/exec` or network packages (static test); `engine/skills` gains a `TestMain` guard isolating `HOME` and the state home.
- **Approval record semantics.** The record names the skill id, the SHA-256 of the exact `SKILL.md` bytes, the time, and the approver label. A record whose digest no longer matches the file is invalid. The engine cannot prove a human ran `approve`; that limit is declared.
- **Stale docs** fixed: the contract section that still says Codex body loading is unverified; the overlay usage text that omits `lint` and `project-*`.

## Acceptance criteria

- `skills add` for a global skill without a matching approval record is refused and writes nothing; with a record whose digest matches the exact file bytes it succeeds; changing the file after approval invalidates the record.
- The grandfathered baseline is fixed and tested: a baseline skill validates without a record; a skill outside it does not.
- The guard denies `skills approve` issued by the agent with a reason, never blocks other commands, and its family installs, uninstalls, and reports status preserving foreign entries.
- Concurrent `skills add` and `install` invocations are serialized; registry and manifest never disagree after any interleaving; a busy lock is reported, not waited on forever.
- `skills install` replaces only files it owns unmodified, refuses a foreign directory or a hand-edited file naming the path, covers `.claude/skills` and `.agents/skills`, and is idempotent; `skills adopt` is explicit.
- `runtime capabilities` reports `skills` per runtime with evidence naming existing tests, and states the global-tier dependency on `labdrian apply` as a limit.
- One acceptance test walks: draft outside `skills/` → lint → approve → add → manifest sync → install → project register, revise, retire → drift detection → report-only retirement (project tier).
- No new code imports `os/exec` or network packages; no test touches real user state.

## Risks and points to confirm at approval

- The approve guard is a speed bump: an agent with `Bash` can write the record file by hand. What is guaranteed and tested is that the record matches the exact skill bytes.
- The hook needs `install-hooks` re-run and a Claude Code restart, on separate approval.
- The global tier still depends on `labdrian apply`; the declaration says so.
- The user verifies the phase personally at the end, with a live check.
