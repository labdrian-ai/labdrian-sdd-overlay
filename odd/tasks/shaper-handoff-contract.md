## Objective

Specify a runtime-neutral, versioned, machine-only JSON handoff from exploration/prototyping to a bounded plan. The record describes architecture, stages, roles, tests, acceptance, risks, estimates, memory scope, and delivery limits. It is not rendered into a human-facing document and is not an execution or permission mechanism.

## Problem and boundary

The Phase 3 roadmap outcome calls for a bounded plan and rejection of incomplete, contradictory, or out-of-scope handoffs. A structural schema can deterministically reject malformed or incomplete records and detect some exact declared-scope conflicts. It cannot, by itself, understand plain-English contradiction or determine whether natural-language work is within a Goal's intent. Those judgments require human review and evidence.

Phase 3 specifies the handoff record and its validity/readiness distinction. **Phase 4 — Reusable roles** remains a separate roadmap outcome; no role execution, typed role-to-role handoff system, or Phase 4 implementation is included here.

## User-approved requirements

The following are settled requirements for the specification and are not reopened here:

1. The handoff is versioned JSON used for machine-to-machine exchange only; there is no rendered human document.
2. Missing required fields and explicit scope violations are deterministically rejected.
3. Semantic contradictions are flagged for human resolution, not automatically adjudicated by a language evaluator.
4. A handoff with flags may parse and remain a draft. It cannot become ready until every flag has an evidenced human resolution and the currently active agent runtime has presented the exact Goal and plan for a human decision independent of Shaper-authored JSON. The runtime-owned interaction must bind its decision to the exact presented content; a content hash may detect drift but is not identity or a signature. This host-owned decision is required before every ready outcome, including when there are zero flags. Phase 3 specifies this interaction contract but cannot claim a positive ready outcome until at least one real runtime integration supports it and real human input is evidenced. No runtime is selected here or capability claimed. Phase 7 owns the broader runtime-adapter work. Shaper-authored JSON alone cannot supply clearance.
5. Scope must be checked against both the source Goal's `scope` and `non_goals`, and the handoff's own declared limits. An absent or unverifiably bound Goal cannot yield a ready handoff.
6. Structural validity and readiness are separate outcomes. Natural-language contradictions and out-of-scope judgments cannot be structurally inferred. Any exact-string comparison is only a limited deterministic subset, not proof of semantic consistency.
7. `project_id` is the shared project-context matching key, not a unique Goal identity; multiple Goals for one project may run concurrently, without forced global sequencing, and may share one observed Git worktree. `goal_id` distinguishes a Goal within that project. For each readiness evaluation, the caller supplies the explicit Goal v2 JSON file to evaluate; this is a per-evaluation selection, not a persistent Goal catalog or an assertion that the file is the authoritative/current Goal among other files. Resolve the actual file inside the canonical Git worktree observed and verified for that evaluation. Reject a missing or ambiguous source, symlinked source, traversal, or any resolution that escapes that worktree; do not infer Goal identity from a branch or path. Strictly parse Goal v2 and require both `project_id` and `goal_id` to match the handoff. Record the source provenance and the exact Goal content or revision-like content evidence evaluated. A content hash may detect content drift, but cannot establish authoritative currentness, completion, or closure. The user-approved worktree decision remains evaluation-time provenance: there is no persistent `worktree_id` registry or lifecycle prerequisite for Phase 3. The observed root/branch/provenance is transient evidence, not a durable unique identifier; paths and branch names alone are not stable IDs, and an observed root must not be labeled a durable `worktree_id`. Missing or unverifiable Git worktree provenance leaves the handoff draft-only. This observation cannot prove Goal currentness, cross-session memory matching, fulfillment, or execution authority. Goal v2 was committed locally in a separate worktree; it is not integrated into this checkout or implemented as Phase 3 runtime behavior. Do not claim Goal v1 implements `goal_id` or treat proposed field shapes as approved schema.
8. Execution evidence is confined to its own Goal/worktree. Reusable procedural memory may be available at project scope and tagged with originating Goal/worktree provenance; do not create per-worktree Engram/longterm-mem project identities, independent memory silos, or invent memory write/promotion authority. `longterm-mem/internal/projectid/projectid.go` explicitly excludes `WorktreeRoot` from project identity. Context-sensitive filtering/provenance across Engram, longterm-mem, and procedural memory is a future design goal, not existing support.
9. Each acceptance criterion that cannot be deterministically verified requires human adjudication with evidence. Deterministic criteria require actual check results; human adjudication does not replace those results.
10. Every Goal closure requires a final explicit human confirmation, even when all deterministic checks pass. A Shaper handoff may plan evidence and checks, but may not declare the Goal satisfied or closed. Goal fulfillment and closure are downstream lifecycle work, not Phase 3 behavior; exact later-phase ownership remains undecided.
11. Estimates cover agent effort to execute the Goal's stages, not effort to prepare or validate the plan. Count agent work only; exclude human labor. The unit, time basis, scalar versus range representation, and any other estimate schema remain open.

## Proposed contract behavior

### Validity

Validity answers only whether the JSON record is supported and structurally well-formed. The proposed validator deterministically rejects malformed JSON, unsupported versions, missing or invalid required fields, and explicit scope violations that the chosen structural rules can establish. Validity does **not** mean the plan is consistent, within Goal scope, approved, ready, or executable.

### Draft and readiness

A valid record may be a draft. A record with contradiction or scope-review flags may parse and remain structurally valid, but is not ready. Readiness is a separate assessment and requires, at minimum:

- the caller-designated Goal v2 JSON file for this evaluation, strictly parsed and matching both `project_id` and `goal_id`, plus Git worktree provenance observed and verified at readiness-evaluation time. Resolve the actual file within the canonical observed worktree; reject absence, ambiguous source resolution, symlinked source, traversal, and escape from that worktree. The caller's designation selects the input for this evaluation only: it does not establish that the file is the authoritative/current Goal if duplicate or competing Goal files exist. Record source provenance and the exact Goal content or revision-like content evidence evaluated. A content hash may detect drift but cannot prove authority, currentness, completion, or closure. Missing/unverifiable worktree provenance leaves the record draft-only. This worktree observation is transient evidence, not a persistent `worktree_id` identity or registry lookup. Multiple Goals may share one observed worktree;
- review of the handoff against both bound Goal `scope` and `non_goals`, as well as its own declared limits;
- no unresolved contradiction or scope-review flags; the currently active agent runtime presents each flag and captures its human resolution, including a reason and evidence for each flag;
- an affirmative human semantic clearance captured by the currently active agent runtime before this ready outcome, even when there are no flags. The runtime presents the actual Goal v2 content and exact plan payload, Goal `scope` and `non_goals`, the handoff's own declared limits, and all flags. The human resolves every flag with a reason and evidence before giving an overall affirmative clearance, independently of Shaper-authored JSON. Bind the decision to the exact presented content; a content hash is drift detection only, not identity or a signature. Phase 3 cannot claim a positive ready outcome until at least one real runtime integration supports this interaction and real human input is evidenced; mocks alone are insufficient. No runtime is selected and no runtime capability is claimed. Phase 7 owns broader runtime-adapter coverage. A Shaper-authored field or claim is not this host-owned decision;
- a valid host-owned clearance record kept separately from the authored handoff payload. It binds to the exact Goal content and exact plan payload plus their provenance as observed at the readiness evaluation, records the human action and only actor identity verifiably established by the host (a displayed label alone is not verified identity), and records time if available. Any change to either bound subject invalidates the record. The record shape and binding mechanism remain open; do not create a circular subject digest by putting the clearance record inside the payload it binds;
- a proposed verification method or human adjudication path for each acceptance criterion; actual deterministic check results and human adjudications are downstream fulfillment evidence, not prerequisites for accepting a plan as ready. Completed Goal criterion results are not a readiness prerequisite.

Goal binding and Goal closure are separate concerns. `project_id` matches shared project context and `goal_id` distinguishes Goals. The caller supplies a specific Goal v2 JSON file on each readiness evaluation; it is the selected evaluation input, not a persistent catalog or authoritative-currentness claim. The file must resolve unambiguously within the canonical Git worktree observed for that evaluation, without symlink, traversal, or escape, and must strictly parse as v2 with both IDs matching. Record its provenance and the exact Goal content or revision-like content evidence evaluated. A hash can detect content drift only; it cannot prove authoritative currentness, completion, or closure. Readiness separately observes and verifies Git worktree provenance at evaluation time. The observation is transient, not a durable unique ID, and does not prove Goal currentness, cross-session memory matching, fulfillment, closure, or execution authority. Multiple Goals may share the same observed worktree. The positive `ready` outcome and runtime-owned human interaction contract are Phase 3 specification scope, but neither is implemented or evidenced yet. Phase 3 cannot claim a positive ready outcome until at least one real integration with an agent runtime supports the interaction and real human input is evidenced; mocks alone are insufficient. No runtime is selected or capability claimed. Phase 7 handles broader runtime adapters. The Shaper may specify planned evidence and checks but cannot declare Goal satisfaction or closure. Any Goal closure, which is downstream of Phase 3, requires a final explicit human confirmation even if deterministic checks pass.

A missing or unverifiable Goal file or worktree association, an unresolved/ambiguous source, an invalid Goal v2 document, either ID mismatch, an unresolved flag, absent required resolution evidence, or absent/invalid host-owned semantic clearance prevents readiness. The model does not search a persistent catalog or choose among duplicate files; unresolved competing-source ambiguity fails closed for that evaluation, while the caller's selection alone does not settle which file is authoritative/current. If a trustworthy human decision channel or valid binding is unavailable, the handoff remains a draft. A captured human action is evidence that an explicit decision was made; it is not proof that the human carefully read the material, permission to execute, RDD review, Goal fulfillment, or final human Goal closure. This specification grants no execution authority: even a ready handoff does not authorize or dispatch work. The exact evidence representation and any runtime meaning of “executable” remain open; no execution behavior is proposed here. A clean positive `ready` case remains prospective, not fully specified: it depends on resolving host-owned clearance and flag evidence, scope-review rules, and estimate and wire-field shapes. These are open schema/product decisions, not implied defaults.

### Limits of structural detection

An implementation may detect an exact item appearing in both an actionable list and a declared exclusion list. That catches only literal, machine-comparable cases. It does not prove that differently worded items agree, that an item is semantically in scope, or that two plan statements do not contradict one another. Do not claim natural-language validation or complete out-of-scope detection. Matching normalization and the full scope-review method remain open; no trimmed-equality, substring, or case-folding rule is approved here.

## Rejection, flagging, and resolution model

| Condition | Proposed handling | Outcome |

## Slice S — authorized deterministic implementation

**In scope.**

- Field-agnostic strict wire validation in shared package `engine/jsonstrict`, reused by `engine/goal` and `engine/shaper`.
- Worktree containment in a shared exported package `engine/pathguard`, moved from the reviewed unexported helpers in `engine/skills/pathguard.go` with no behavior change, so containment is never implemented twice.

The binding result is evidence for a later readiness evaluation; it is not readiness.

**Excluded.** Runtime-owned human clearance, flag representation and resolution, readiness evaluation, any positive `ready` outcome, execution authority, persistent Goal catalogs or `worktree_id` registries, and Git worktree provenance verification beyond containment inside the caller-supplied root.
