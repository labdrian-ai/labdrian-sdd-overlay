# Decision — Standalone Platform Master Roadmap

**Authority:** sole active roadmap for the standalone product and its shared workflow, memory, skills, runtime, and release layers.
**Decision date:** 2026-09-21
**Scope:** Labdrian standalone platform; this document reconciles phase, product-package, and SDD sources without treating their numbering as equivalent.

## Decision and authority boundary

Use the stable **Phase 0–10** sequence below as the canonical standalone-product work register. Product packages **P0–P8** are source aliases, not a second schedule; historical SDD IDs remain provenance or distinct linked work. The two ODD task ledgers retain detailed execution checks and evidence but do not define separate roadmap outcomes. The supporting product narrative is [Standalone product roadmap rationale and crosswalk](../../docs/architecture/standalone-product-roadmap.md); the entry guide is [Standalone product start here](../../docs/architecture/standalone-product-start-here.md).

`openspec/project/roadmap.md` is a generated **historical SDD mirror, v7**, not an active standalone-product roadmap. Its stated canonical Engram source is observation #2067; the supplied current context identifies that source as **v11 with eight appendices**. Do not regenerate or edit the historical mirror in this reconciliation. The v7 mirror and this supplied v11 locator disagree in version; v11's detailed rows/appendices were not independently available for verification here. Preserve historical SDD IDs and treat any status not corroborated by current task evidence as `unverified`.

No roadmap status grants implementation, remote-operation, review, delivery, or release authority. Statuses below describe available evidence only. `unverified` means the outcome's current implementation/acceptance state was not checked. A title match is not completion evidence.

## Product boundaries

- Labdrian is a platform above existing agent runtimes, not a replacement execution loop.
- Gentle AI and gentle-pi are optional compatibility integrations, never standalone prerequisites.
- `longterm-mem` remains separate; episodic, semantic, and procedural memory remain distinct.
- Human authorization and actual runtime controls govern permission, admission, delivery, and release; model/profile output cannot grant authority.
- Unsupported, unavailable, failed, skipped, and unverified capabilities remain distinct. Advertise runtime support only with observed evidence.
- Preserve foreign configuration and user memory; no implicit model download, remote access, or destructive migration.

## Sequencing and completion

The canonical phase order is 0 → 1 → 2 → 3 → 4 → 5 → 6, with runtime adapters, skill lifecycle, observability, and release following their explicit phase sequence. The original source also places Phase 7–10 in that order; this register does not add dependency edges beyond that stated sequence. Package-specific tasks and historical SDD dependencies require their own source evidence before scheduling.

A work item is complete only when its own acceptance evidence, known limitations, and current lifecycle/check evidence are recorded. Do not infer implementation completion from the roadmap, matching titles, an old SDD status, or a checked-looking unrelated ledger. Roadmap approval is not authorization to implement, publish, access remotely, or release.
