## Exploration: longterm-mem-knowledge-ingestion

### Current State

`longterm-mem`'s only intake path is: agent calls Engram `mem_save` (MCP) → observation lands in Engram's own SQLite DB → a human or agent calls `promote{project, engram_id}` (MCP tool, `longterm-mem/internal/mcpserver/server.go`) or `longterm-mem promote --id N` (CLI) → `promote.ExplicitPromote(writer, store.ObservationByID, id)` (`internal/promote/explicit.go`) looks the observation up via `engram.Store.ObservationByID` (`internal/engram/store.go`, strictly read-only DSN `mode=ro&_query_only=true&_txlock=deferred`) and calls `Writer.Promote(obs, true)`. There is no batch/URL/document/directory ingestion tool anywhere; `index`, `index --embeddings`, `sync`, `status`, `stale`, `doctor` (README.md) all operate on content already in Engram or already promoted — none accept new external content.

**Central architectural finding (resolves the fork this exploration was scoped to answer):** `promote.Writer.Promote(obs engram.Observation, explicit bool) (Result, error)` (`internal/promote/writer.go:76`) takes an in-memory `engram.Observation` struct BY VALUE — it does not itself fetch from Engram. `ExplicitPromote` only calls it via an `ObservationLookup func(id int64) (engram.Observation, bool, error)` seam (`internal/promote/explicit.go:15`), production-wired to `store.ObservationByID`. Nothing in `Writer.Promote`, `EmitPage` (`internal/promote/page.go`), or `Allocate` (`internal/promote/address.go`) requires the observation to have actually come from Engram's DB — the vault write path is structurally decoupled from Engram already. So a **direct Go-side ingestion path bypassing Engram entirely is architecturally buildable today** without touching the read-only DB constraint at all: a new command/tool could construct a synthetic `engram.Observation{ID, Title, Content, Project, Type, ...}` from fetched/parsed external content and call `Writer.Promote(synthetic, true)` directly. `Eligible()` (`internal/promote/eligible.go`) always allows `explicit=true` regardless of Pinned/TopicKey.

`longterm-mem` owns three storage surfaces independent of Engram's DB: the git-tracked vault pages themselves (`wiki/memory/*.md`), its own precedence sidecar (`PrecedenceStore`, `.raw/.longterm-mem-manifest.json`, `internal/promote/store.go` — "this file has exactly one writer: this package"), and its own FTS/embedding indexes under `LONGTERM_MEM_STATE_DIR` (`internal/vecindex`, `internal/query/embedarm.go`). None of these are Engram's DB; all are already Go-write-capable.

**Hard blocker for any Go-side network fetch (URL ingestion):** `longterm-mem/net_allowlist_test.go` (package `guard`) statically AST-parses every non-test `.go` file in the module and fails the build if any file other than `internal/embed/client.go` imports `net/http` or `net` (R-071). The comment is explicit: "every other file that reaches out over net/http or net is exactly the workaround that would defeat this guard." A parallel, independent guard exists in `engine/skills/zero_fetch_test.go` (ADR-15, ImportsOnly AST parse, closed allowlist of stdlib-only imports, explicitly excludes `net`/`net/http`/`os/exec`) — showing "zero egress by default, explicit allowlist, reviewer-argued widening" is a repo-wide convention, not a one-off. `internal/embed/client.go` itself only talks to a loopback Ollama endpoint for embeddings (`--allow-remote-embedder` flag required to widen even that). There is currently ZERO HTTP-fetch or document-parsing (PDF/HTML-extract) code anywhere in this repo to reuse; a URL-fetch ingestion path would need either (a) deliberately widening `allowedNetImporters` (a reviewed egress-boundary change per the test's own doc comment) plus adding fetch+extract dependencies to `longterm-mem`'s already-third-party-permissive `go.mod`, or (b) staying agent-driven, where the AGENT (not longterm-mem's Go code) does the fetch via its own tools (WebFetch) and hands longterm-mem already-extracted text.

Dedup/identity: `Allocate`/`findPromotedPage` (`internal/promote/address.go`) key re-promotion reuse on `(project, engram_id)` read from already-written page frontmatter, matched against `obs.ID`. Every comment and field name (`EngramID`, `engram_id` frontmatter key, `promotionFooter`: "Promoted from Engram observation N") assumes `obs.ID` IS a real Engram observation id. A direct-ingestion path supplying a synthetic ID would need its own non-colliding ID space (Engram autoincrements from 1) or the frontmatter contract changes — this is real design surface, not solved here.

### Affected Areas

- `longterm-mem/internal/promote/writer.go`, `explicit.go`, `eligible.go`, `page.go` — the existing Promote/EmitPage/Eligible seam a direct-ingestion path would reuse or extend; `obs.ID`/`EngramSyncID`/`EngramType` frontmatter fields currently assume Engram provenance.
- `longterm-mem/internal/promote/address.go` — `findPromotedPage`/`Allocate` dedup keys on `(project, engram_id)`; a synthetic-ID ingestion path needs an explicit identity/dedup story here.
- `longterm-mem/net_allowlist_test.go` — the R-071 static guard that must be deliberately widened (or left untouched) depending on which approach is chosen; this is the actual fork, not a hypothetical.
- `longterm-mem/internal/mcpserver/server.go` — would need a new tool (e.g. `ingest`) if a direct path is chosen; `promote` currently only accepts a pre-existing `engram_id`.
- `longterm-mem/internal/engram/store.go` — confirmed read-only by construction (R-002); irrelevant to a direct-ingestion design since that path never touches this package.
- `longterm-mem/internal/embed/client.go` — the only existing network precedent (loopback Ollama only); not reusable for arbitrary URL fetch.
- No `internal/vault/`-level fetch code exists (that directory is the shell-subprocess `Runner` for vault scripts like `allocate-address.sh`, unrelated to content fetching).

### Approaches

1. **Ingestion-via-Engram-first (agent always writes an Engram observation, longterm-mem only ever promotes)** — an agent fetches/reads the external source (via its own WebFetch/Read tools, not longterm-mem's Go code), calls `mem_save` on the extracted content, then `promote`s that observation, exactly like today's flow.
   - Pros: zero new Go code in `longterm-mem`, zero egress-boundary change, fully consistent with the read-only-Engram-DB constraint and with `EngramID`/dedup semantics already baked into every field name and comment; content becomes `mem_search`-findable through the normal episodic layer.
   - Cons: couples ALL new-knowledge intake to an agent turn — no non-agent-triggered batch/directory ingestion is possible this way; large documents get filtered through Engram's episodic-memory conventions (session-scoped observations, `mem_save` size/format norms) which may not fit a big PDF or a batch of files well; still one-at-a-time promotion unless a batch-promote command is added separately (that's a sync-time concern, largely orthogonal).
   - Effort: Low (mostly convention/skill work, not new Go surface).

2. **Direct ingestion inside `longterm-mem` itself (new Go command/tool bypassing Engram, writing straight to vault+index)** — a new subcommand/MCP tool takes a URL/file/directory, does fetch+extract IN GO, builds a synthetic `engram.Observation`, and calls `Writer.Promote(synthetic, true)` directly, skipping Engram entirely for that content.
   - Pros: no agent-turn coupling, enables batch/directory/scheduled ingestion, reuses the already-decoupled `Writer.Promote` seam (confirmed structurally free of the read-only-DB constraint).
   - Cons: **requires deliberately widening the R-071 net-import allowlist** (a reviewed egress-boundary decision, not a small add) and adding new fetch/parse dependencies (`longterm-mem`'s `go.mod` allows this, `engine/`'s zero-dep boundary does not apply here); content ingested this way is invisible to `mem_search`/Engram — Engram has no read path into vault pages, so this creates a second, disconnected provenance/discovery surface; needs a synthetic-ID scheme that does not collide with real Engram ids and a rewrite of every "Promoted from Engram observation N" assumption in frontmatter/footer/dedup code; duplicates dedup logic Engram would otherwise give for free (Engram's own recall/supersession machinery, imperfect as CLAUDE.md's own memory notes already flag, does not apply to this path at all).
   - Effort: Medium–High.

3. **Hybrid: agent-driven fetch, Go-side batch/document extraction as a local (non-network) helper** — agent still does any network fetch (approach 1's boundary respected: R-071 untouched), but a new Go helper inside `longterm-mem` accepts already-fetched raw text/files (local paths, or text handed in-process) and does structured extraction/chunking before constructing the observation payload the agent then `mem_save`s — i.e., Go helps with parsing large/structured content, never with fetching it.
   - Pros: keeps the net-egress boundary untouched (satisfies R-071 without a review fight), still funnels everything through Engram (dedup/`mem_search`/relation-inference machinery stays authoritative, per this session's declared out-of-scope for connection-inference), gives a real answer for "a pasted/uploaded document" or "a directory scan" without needing HTTP fetch at all.
   - Cons: still requires an agent turn per ingestion event (does not solve fully autonomous/scheduled ingestion); does not solve "ingest a URL" without an agent-side fetch step; local-file/directory scanning still needs new Go code and its own tests, though no egress-boundary change.
   - Effort: Low–Medium.

### Recommendation

**Approach 1, with Approach 3 as the natural next increment.** The stated goal is memory that is "accessible and scalable, able to reason and create new connections" — that reasoning/connection machinery is explicitly Engram's (`mem_compare`/`mem_judge`), confirmed by this session's own scoping. Approach 2 ingests content that Engram (and therefore `mem_search`, relation inference, and every future "reason and create new connections" capability) can never see, which directly undermines the stated goal rather than serving it — it is not just riskier, it is the wrong destination for content this project wants to reason over later. It also requires reviewing and widening a guard (R-071) whose own doc comment says widening is "a change to the egress boundary, not a convenience," and it forces solving a synthetic-ID/dedup problem this exploration shows has no existing answer. Approach 1 costs nothing architecturally (the flow already exists end to end) and Approach 3 extends it cleanly for large/structured documents without ever touching R-071. A future slice could still revisit direct ingestion once/if there's a concrete case for content that deliberately should NOT enter Engram's reasoning layer — but that should be an explicit, argued decision at `sdd-propose`/`sdd-design` time, not a default.

### Risks

- **R-071 net-import guard is a hard, tested blocker for any Go-side URL fetch inside `longterm-mem`** — confirmed via `net_allowlist_test.go`, not assumed. Any proposal choosing Approach 2 must explicitly argue for widening it.
- **Synthetic-ID / dedup has no existing design.** `EngramID`, `engram_id` frontmatter, and `findPromotedPage`'s `(project, engram_id)` dedup key all assume Engram provenance throughout `internal/promote/*`; a non-Engram-sourced observation has nowhere safe to put its identity today without risking collision with real Engram ids.
- **Directly-ingested content (Approach 2) is invisible to Engram's own recall/relation machinery** — `mem_search` has no read path into vault pages, so anything ingested outside Engram cannot benefit from `mem_compare`/`mem_judge`-driven connection-making, which is the umbrella goal's other explicit pillar (out of scope for this slice, but a real downstream cost of Approach 2).
- **No existing fetch/parse code to reuse anywhere in the repo** — any URL/PDF ingestion, whichever approach, is net-new dependency surface; only the agent's own existing WebFetch tool is a genuine zero-new-code option today.
- **Legacy claude-obsidian address-allocation dependency is orthogonal to this fork** — `Allocate` shells out to `scripts/allocate-address.sh` (a vault-owned script) regardless of which approach supplies the observation; a direct-ingestion path would hit the exact same allocation script, so it does not make that legacy coupling worse or better — it is unaffected either way.

### Ready for Proposal

**Yes** — the central fork this exploration exists to resolve (Engram-first vs. direct) is answered with code-level evidence: direct ingestion is structurally buildable at the `Writer.Promote` layer but is blocked by a deliberate, tested egress guard (R-071) and lacks any synthetic-ID/dedup design, while Engram-first costs nothing new and directly serves the stated "reason and create new connections" goal. Recommend `sdd-propose` proceed with Approach 1 (agent-driven `mem_save`-then-`promote`, formalized as an ingestion convention/skill rather than new Go surface) with Approach 3's local-parsing helper as an explicitly named follow-on increment for large/structured documents.
