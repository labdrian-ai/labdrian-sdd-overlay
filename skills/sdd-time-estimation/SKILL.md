## Activation Contract

Use this skill when the user or orchestrator asks for time, effort, complexity, delivery window, or implementation scope for a requirement before starting SDD execution. Treat the estimate as a pre-start planning report tied to likely SDD phases.

**Default execution model is agent-orchestrated.** Unless the user states the work will be implemented by a human directly, assume delivery goes through `inception-pipeline`-orchestrated AI sub-agents (`sdd-apply`, `sdd-verify`, review lenses, judgment-day judges). Agent-compute-time and human-implementation-hours are different units running at different rates — never blend them into a single number.

## Hard Rules

- **Three units, independently measured, never blended (R-001/R-002):** agent-compute-time, elapsed-calendar-time, and human-confirmation-checkpoint-count are three separately tracked units. Any report showing two or more of them MUST show them under separate labels — never summed or averaged into one figure.
- Inspect only the relevant workspace and requirement context before estimating.
- If SDD artifacts already exist, use them in this order: proposal, spec, design, tasks. If they do not exist, estimate from the requirement and state assumptions.
- **The headline range is agent-compute-time, not human-implementation-hours.** Build it from per-phase throughput (see Execution Steps) calibrated against this project's own `sdd/*/actuals` records. A human-equivalent-hour figure may still be reported, but only as a secondary complexity/tiering signal — it must never be the number presented as "how long this takes."
- Be conservative within each unit separately: don't return optimistic agent-compute-time, and don't inflate it using human-effort intuition either — that reintroduces the exact bias this skill exists to avoid.
- Give ranges, never a single exact duration.
- **No sample-count precondition, ever:** a brand-new project with zero prior `sdd/*/actuals` records (`n=0`) is the expected first-use state, not a blocked one. Produce the estimate immediately from the Bootstrap defaults below and flag confidence Low — never wait for, ask for, or require any number of prior estimations before running. `n>=3` (see the calibration rule below) only unlocks a sharper per-unit rate; it is never a precondition for producing an estimate at any `n`.
- Ask questions only when missing information blocks estimation; otherwise continue with explicit assumptions.
- Include a contingency buffer whenever there is cross-system work, unclear rules, sensitive data, migration risk, or external dependency risk.
- Track estimation accuracy after work closes: compare planned estimate, agent-compute-time actually spent, human review effort, post-review fixes, and final approval/cierre time.
- Treat "actual time" as the full process time until human review approval, not only the first SDD implementation/verification pass.
- **CALIBRATION (pre-start, read-only):** At pre-start, READ `project/{project}/estimation-calibration` if present, and `mem_search` for `sdd/*/actuals` records for this project (writer: `inception-pipeline` closure-feedback — see `../_shared/pre-sdd-contracts.md`).
  - **This step never blocks first use.** A brand-new project with zero `sdd/*/actuals` records is `n=0`, the default starting state, not a missing precondition — proceed straight to producing the estimate with the Bootstrap defaults below and Low confidence. Nothing here requires 1, 2, or 3 prior estimations to exist before this skill can run.
  - Build the per-phase agent-compute-time baseline ONLY from each actuals record's `implementation_hours`, `review_gate_hours`, and `post_review_fix_hours`. **WHEN one or more of these three fields is absent under R-019** (compute-time fields stay unpopulated until a durable source exists), the record supplies NO compute-time numerator for the affected phase — never substitute `total_wall_clock_hours` or any other elapsed-time figure in its place. State the consequence explicitly rather than dividing over an absent value: with the numerators absent, the per-unit compute-time rate cannot be computed, so confidence falls back to the disclosed bootstrap defaults / qualitative scaling regardless of calibration `n`.
  - **Name the REAL blocker on the compute-time rate: it is a SAMPLE CEILING, not unreachability.** Both actuals records committed to this repository — `engine/skills/testdata/corrected-actuals-skills-validate-ondisk-gate.json` and `engine/skills/testdata/corrected-actuals-sync-check-repo-behind-origin.json`, mirroring Engram `sdd/skills-validate-ondisk-gate/actuals` (obs #2789) and `sdd/sync-check-repo-behind-origin/actuals` (obs #2096) — DO carry all three numerators. The compute-time baseline therefore stands at `n=2`, one sample short of the `n>=3` branch below, which is reachable in principle and frozen in practice. What freezes it is R-019 going FORWARD, not the historical records: every record written after R-019 leaves those three fields empty, so no future closure can raise `n` past 2. Report this as **`n=2` (ceiling)**, never as "unreachable by construction" — that phrasing is false against the bytes on disk and it tells the reader the wrong repair. Two things lift the ceiling, and the report MUST name them: (a) a durable per-phase duration source appears — R-019 states exactly what is missing today, namely that orchestrator telemetry is session-transient, the `sdd-attempt` ledger has no timestamp fields, and transcripts carry no structured subagent durations — after which R-019's deferral no longer applies and `n` can grow again; or (b) a further pre-R-019 record is recovered that also carries all three numerators. Until one of those happens the `n>=3` rate is unreachable **for this project at this time**, which is a smaller and truer claim than unreachable by construction.
  - `total_wall_clock_hours` is NEVER an input to the agent-compute-time baseline — it measures elapsed calendar time (tiering-go-ahead to merge, including interruption gaps), a distinct unit that must stay separately labeled, never folded into the compute-time sum.
  - As a read-only delivery-window diagnostic, derive round-trip latency only from interruption-clean residual samples with positive `checkpoint_count`, using `(total_wall_clock_hours − sum(phase hours)) / checkpoint_count`. Exclude any residual known or narrated to include a session, rate-limit, or provider interruption from the round-trip-latency calibration `n` and rate; never subtract a guessed interruption amount from a contaminated residual. When no interruption-clean residual sample exists, use a disclosed bootstrap default marked Low confidence. Keep interruption allowance separate and fixed, explicitly marked uncalibrated until independent interruption evidence exists.
  - **That exclusion is R-011 law and it has a selection bias — say so, and stop throwing the sample away.** Discarding a contaminated residual is a filter, and what it selects for is precisely the work least like what anyone asks to be estimated: an interruption-clean residual is by definition a change that finished inside one uninterrupted session, so the surviving samples are short single-session changes while the long multi-session ones — the ones whose delivery window is actually in question — are the ones deleted. On this project's own two records the bias is measurable, not hypothetical: the retained clean sample gives `(6.64 − 1.39) / 7 = 0.75` h per checkpoint, while the discarded contaminated sample would give `(36 − 1.36) / 12 ≈ 2.89` h per checkpoint — **3.9× higher**. The rule keeps the optimistic sample and deletes the pessimistic one, and any report using the clean rate MUST disclose that.
  - **Record the interruption DURATION instead of losing the sample.** closure-feedback MUST record the observed interruption duration for a change as a labelled `interruption_hours: <n>` figure inside `variance_vs_plan`, naming its cause (session reset, provider rate limit, human unavailability). It is deliberately NOT a new schema property: R-003/R-004/R-005 forbid adding any property to the actuals record and `additionalProperties: false` is unchanged, so this rides the same prose-disclosure precedent R-006/R-007/R-008 already set for the durable-vs-reconstructed checkpoint split — and it inherits that precedent's stated cost, that free text is not machine-verifiable. Use it in exactly two places: (1) as the disclosed evidence that finally calibrates the interruption allowance, which stays fixed and marked "uncalibrated" until at least two recorded interruption durations exist; and (2) as a REPORTED-ONLY interruption-adjusted residual, `(total_wall_clock_hours − sum(phase hours) − interruption_hours) / checkpoint_count`, shown beside the clean rate so both are visible. That adjusted figure MUST NOT enter the round-trip-latency calibration `n` or rate while R-011 stands: R-011 forbids adjusting a contaminated residual, and this rule records the adjustment rather than applying it. It becomes a calibration input only if R-011 is amended to admit measured — never guessed — interruption durations. Recording it now is what makes that amendment arguable later; discarding the sample is what has kept it unarguable.
  - State confidence by sample size — this scales confidence only, it never gates whether an estimate runs: `n=0` → no project baseline, use the stated bootstrap defaults below and flag Low confidence; `n=1-2` → Low/Medium confidence, scale qualitatively by relative complexity (this change vs. the calibration change's known scope); `n>=3` **and** the actuals records carry the optional complexity-unit fields (`requirement_count`, `changed_lines`, `review_lens_count`, `checkpoint_count`) → compute an explicit rate per unit (`implementation_hours / changed_lines`, `implementation_hours / requirement_count`, `review_gate_hours / review_lens_count`) and raise confidence accordingly; if `n>=3` but the complexity-unit fields are missing on older records, fall back to qualitative scaling and note that the rate will sharpen once enough records carry the new fields.
  - `review_lens_count: 0` is a legitimate Low-risk "no lens" outcome, not a missing value — exclude those records from the `review_gate_hours / review_lens_count` division (it would be undefined) and fold their `review_gate_hours` into the verify-only baseline instead.
  - **Only three of the four listed complexity-unit fields are divisors, and they do not all have the same `n`.** `requirement_count`, `changed_lines`, and `review_lens_count` are divisors in the three rates above; `checkpoint_count` is listed alongside them but divides nothing there — it is the divisor of the round-trip-latency rate instead, a delivery-window diagnostic, not a compute-time rate. Do not report `checkpoint_count`'s presence as evidence that the compute-time rate is ready. Per-divisor sample counts on the two records currently on disk: `requirement_count` and `changed_lines` are present on both (`n=2`); `review_lens_count` is present on `skills-validate-ondisk-gate` only and absent on `sync-check-repo-behind-origin` (`n=1`), so the `review_gate_hours / review_lens_count` rate is a single-sample rate and falls under the SINGLE-SAMPLE HONESTY rule below even if the overall `n>=3` gate is ever met.
  - Never hide misses — if a phase consistently overruns its baseline, widen that phase's range instead of anchoring low.
- **Bootstrap defaults (used only when zero project calibration data exists):** these are agent-compute-time, not human hours — proposal/spec/design/tasks (planning phases, mostly single-agent drafting): 0.1-0.4h combined for a Low/Medium complexity change; apply (implementation): 0.2-1.5h depending on changed-line bucket; verify + review gate (including judgment-day rounds): 0.2-1.0h; post-review fixes: 0.05-0.3h. Treat these as placeholders to be replaced by this project's real calibration after the first change closes — never present them with the same confidence as a calibrated rate.
- **PERSISTENCE (mandatory, pre-start only):** After producing the estimation report and before implementation starts, call `mem_save` with topic key `sdd/{change}/estimate` and `capture_prompt: false`. The saved record must carry: `planned_range_hours` (low/high, agent-compute-time basis), `human_equivalent_hours` (low/high, secondary signal), `expected_checkpoints` (count), `complexity`, `confidence`, and the calibration `n` used. Use the `change` slug inherited from the requirements/entry chain — never re-derive it. See `../_shared/pre-sdd-contracts.md` for topic-key authority.
- **PLAN-VS-ACTUAL PAIRS (a variance claim needs both sides recorded, or it is theatre):** exactly two planning quantities on this project have a matching realized quantity. Every variance statement MUST name which pair it is comparing and where each side is recorded.
  - **Checkpoints.** Plan side: `expected_checkpoints`, persisted by the PERSISTENCE rule above into `sdd/{change}/estimate` before implementation starts. Actual side: `checkpoint_count` in `sdd/{change}/actuals`, written by `inception-pipeline` closure-feedback over the same tiering-go-ahead-to-merge boundary, so the two are measured against one boundary and are directly comparable. Report them as a pair with their delta in Output item 14. Worked example from this project's own record: `skills-validate-ondisk-gate` planned 4 and realized 7 (+75%), because `interaction_mode: auto` suppresses SDD product questions but suppresses neither review consent, budget-authority decisions, nor outward-action authorizations.
  - **Review slices.** Plan side: the number of entries in `review_slices` in `sdd/{change}/entry` — the entry contract requires at least one, each carrying its own `estimated_changed_lines`. Actual side: the realized slice count, meaning how many review candidates actually landed. No structured field for the realized count exists anywhere in the actuals record, so record it as a labelled `realized_slices: <n>` figure in `variance_vs_plan`, on the same prose-disclosure precedent and with the same non-machine-verifiable cost as `interruption_hours` above. Until it is recorded, write "realized slice count not recorded" rather than reusing the planned number as though it were the outcome. Worked example, reproducible from two committed artifacts: `longterm-mem` planned 18 slices and delivered 82 — the plan side is the 18 `review_slices` entries in `openspec/changes/archive/2026-09-02-longterm-mem/entry.json`, the realized side is the 82-PR chain that change's own `archive-report.md` records ("`#176` draft + `#177`–`#258`"). The plan number alone would have reported a 4.6× overrun as if it were the plan.
  - Do NOT invent a third pair. Agent-compute-time has a plan side and, under R-019, no future actual side; presenting a planned-vs-actual compute variance for any change closed after R-019 is comparing a number against an absent one and MUST be reported as such.
- **SINGLE-SAMPLE HONESTY (a confidence word is not a disclosure):** WHEN a reported rate rests on a single sample, the figure MUST carry inline — not in a footnote, not as an adjective — its sample size, the identity of the record it came from, and the observed miss factor against the nearest independent evidence. "Low confidence" tells a reader to discount the number but not by how much or in which direction, and those are the only two things that change a plan. Worked example, reproducible from this repository alone: the round-trip-latency rate is `0.75` h per checkpoint at `n=1`, from `sdd/skills-validate-ondisk-gate/actuals` as `(6.64 − 1.39) / 7`; the one other record on disk, excluded as interruption-contaminated, implies `≈2.89` h per checkpoint as `(36 − 1.36) / 12`, so the shipped rate is at least **3.9× optimistic** against the only comparison that exists — and that factor MUST appear wherever the 0.75 rate appears. State a miss factor only when its arithmetic is reproducible from a cited record. WHEN a larger miss has been observed but its inputs live in no durable record, say "a larger miss was observed but is not reproducible from a recorded sample" and give the reproducible factor instead; never quote an unverifiable multiple, because an invented precision about imprecision is the same failure this rule exists to stop.

## Decision Gates

| Situation | Action |
|---|---|
| New project, no project calibration data yet (`n=0`) | **Never a blocker.** Use the bootstrap defaults, mark confidence Low, and state explicitly that the range will tighten after this change closes. Produce the estimate now — do not wait for prior estimations to accumulate. |
| Clear, simple requirement | Estimate directly with low buffer and high-confidence assumptions. |
| Unknown systems, rules, or data | Estimate with stated assumptions and medium buffer. |
| Cross-system or production-impacting change | Use high buffer, highlight dependencies, raise risks early. |
| Ambiguous requirement | Ask the minimum blocking questions and also provide a provisional estimate. |
| Missing requirement or SDD input | Request the requirement or available SDD artifact summary first. |
| Completed SDD with human review | Record actual agent-compute-time, review/fix time, approval time, variance, and lessons for future estimates. |

## Execution Steps

1. Classify the request: new feature, change request, bug fix, validation rule, integration, reporting change, data change, documentation update, or process improvement.
2. Read the smallest relevant project surface needed to size impact: target workspace, touched modules, likely integrations, existing tests, and deployment/runtime constraints.
3. Define the probable SDD path and which phases will run as delegated sub-agents (proposal, spec, design, tasks, apply, verify, review, archive — the default under `inception-pipeline`) versus any phase a human will do directly.
4. Estimate this change's own complexity units: expected requirement/scenario count, expected changed-line bucket, and expected review-lens count (per the Review Lens Selection tiering: 0 / 1 / up to 4). The changed-line buckets are continuous ranges with a bounded top — `xs 0-149` / `small 150-449` / `medium 450-899` / `large 900-1499` / `xl 1500+`. The first two boundaries are unchanged from the previous table so earlier estimates stay comparable; what changed is the retired open-ended `>450` top bucket, which filed a 460-line change alongside this project's two largest realized changes — 950 and 1456 realized changed lines — a better-than-3× spread inside one bucket, which is no signal at all. `xl 1500+` is the only bucket that stays open-ended, and it is deliberately an escalation rather than an estimate: at that size stop estimating the change and estimate its slices, because it exceeds any single-slice review budget and will be split.
5. For each agent-executed phase, derive an agent-compute-time range by applying the calibration baseline (from the CALIBRATION rule) scaled to this change's complexity units relative to the calibration source. For any human-executed phase, estimate in human-effort hours instead.
6. Separately estimate the expected number of human-confirmation checkpoints (tiering go-ahead, proposal/product decisions, judgment-day rounds, chained-PR split confirmation, merge authorization). This — not feature complexity — is the actual calendar-time driver for agent-orchestrated work; it does not shrink just because compute-time is small.
7. Add a contingency buffer to the agent-compute-time range for ambiguity, coupling, data sensitivity, production risk, and known session/rate-limit interruption risk (calendar time can exceed compute time when a session resets mid-flight).
8. Rate complexity as Low, Medium, High, or Critical — this still drives tiering, chaining, and review-lens selection, independent of the compute-time-vs-human-hour distinction.
9. Rate confidence as Low, Medium, or High, weighted down when calibration `n` is small.
10. If the work is too large for a safe single delivery, recommend SDD slicing or chained PRs and provide phase-level agent-compute-time guidance.
11. Before implementation starts, return the estimation report and **persist the pre-start estimate** per the PERSISTENCE rule.
12. After each SDD completes, update the estimate record with actual agent-compute-time per phase, review findings, fix effort, approval/cierre time, checkpoint count actually hit, variance from plan, and calibration notes — this is what sharpens the next project baseline.
13. Use prior actuals and variance patterns to sharpen future pre-start estimates; never hide misses.

## Output Contract

Return:
1. Summary of the requirement
2. Scope interpretation
3. Estimation table with two sections: (a) **Agent-compute-time per phase** (primary/headline, with the calibration `n` behind each figure), (b) Human-effort-hour equivalent (secondary, complexity/tiering signal only)
4. Total estimated agent-compute-time range (headline)
5. Expected human-confirmation checkpoint count
6. Suggested delivery window — derived from a declared formula: expected checkpoints × round-trip latency + interruption allowance, with every input disclosed. Calibrate round-trip latency only from interruption-clean residual samples with positive checkpoint counts, using `(total_wall_clock_hours − sum(phase hours)) / checkpoint_count`; exclude a sample known or narrated to include a session, rate-limit, or provider interruption from its calibration `n` and rate, and never subtract a guessed interruption amount. When no interruption-clean residual sample exists, use a stated bootstrap default marked Low confidence. The interruption allowance MUST remain a separate, fixed, explicitly-disclosed buffer marked "uncalibrated" until independent interruption evidence exists and does not scale with checkpoint count. Cite the clean round-trip-latency calibration sample and `n`; never present the rate as calibrated when using the bootstrap default. WHEN the rate rests on a single sample, apply the SINGLE-SAMPLE HONESTY rule here in full: print the sample size, the record it came from, and the reproducible miss factor against the nearest independent evidence beside the rate itself — today that means `0.75` h/checkpoint at `n=1` from `sdd/skills-validate-ondisk-gate/actuals`, at least `3.9×` optimistic against the excluded contaminated sample's implied `≈2.89` h/checkpoint. Report `interruption_hours` and the interruption-adjusted residual alongside, as reported-only figures that do not enter the rate.
7. Complexity
8. Confidence level, with the calibration sample size disclosed — and, for every rate resting on a single sample, its reproducible miss factor stated with the confidence word, never instead of it. Where the compute-time baseline is quoted, disclose it as `n=2` (ceiling) and name what would lift the ceiling, not as an unreachable branch.
9. Assumptions
10. Dependencies
11. Risks
12. Open questions, only if needed
13. Final recommendation, including whether to start with SDD discovery/planning and the suggested SDD slices with estimated timing
14. For completed work: Actuals and Calibration section reporting agent-compute-time, elapsed-calendar-time, and checkpoint count under separate labels, never blended — planned vs actual agent-compute-time per phase, review time, post-review fix time, approval/cierre time, elapsed-calendar-time, checkpoints actually hit, variance, and lessons learned. Report the two comparable plan-vs-actual pairs explicitly per the PLAN-VS-ACTUAL PAIRS rule — `expected_checkpoints` vs `checkpoint_count` with its delta, and planned `review_slices` length vs the realized slice count (or "realized slice count not recorded") — and, for any change closed under R-019, state that the planned-vs-actual compute-time comparison has no actual side rather than presenting a variance against an absent number
