# Changelog

## Unreleased

### Added

- `engine/reviewresult`, the contract of what the `reviewer` role returns, as code (own-rdd T1, S1-S2). `reviewresult.Parse(reply, binding)` reads a reply against the candidate the parent launched the reviewer on (the full `base` and `head`, the `diff_sha256` of the canonical diff of the two commits, and the paths of that diff, all handed in as a value) and refuses it, with an error that wraps one named value, at the first rule it breaks: the binding names no candidate (`ErrInvalidBinding`); the reply is not the object of the contract, meaning bytes that are not UTF-8, a key written twice, not one JSON value, or a member missing or null (`ErrUnparseable`; a reply with no `findings` member is not a clean review, `"findings":[]` is); an object has a member the contract does not name, matched by exact name so that `Severity` after `severity` cannot downgrade a BLOCKER (`ErrUnknownMember`); the echoed `base`, `head` or `diff_sha256` differs from the binding (`ErrCandidateMismatch`); `inspection.status` is not `completed` (`ErrInspectionNotCompleted`); the inspected paths are not the paths of the diff, compared as sets, or a path is listed more than once (`ErrPathsMismatch`; a binding that repeats a path is `ErrInvalidBinding`); a null element in `evidence`, `inspection.paths` or `proof_refs` is `ErrUnparseable`; a finding has an `id` that is missing, null or blank (`ErrMissingID`) or that an earlier finding has (`ErrDuplicateID`); a `severity`, `evidence_class` or `causal_disposition` is outside the values the contract lists (`ErrOutsideEnum`); a BLOCKER or CRITICAL lists no proof reference that is not blank (`ErrMissingProof`). A refused reply returns the zero `Result`, and the same reply is always refused for the same reason. It is a domain package in the architecture test: pure standard library plus `jsonstrict`, `gitobject` and `sha256hex`, no file and no git. `labdrian review record` calls it (T2, below). `odd/review-results/README.md` lists the rules.
- Each finding of the reviewer's reply carries an `id` (`F1`, `F2` and so on), unique within the reply, so that the verifier can answer per finding. The delta in `roles/reviewer/body.md` spells it out, and also says that a BLOCKER or CRITICAL needs at least one `proof_refs` entry and that no member is omitted or null; the delta is still four lines. `gadu-generate` rewrote `agents/reviewer.md`, `pi/agents/reviewer.md` and `codex/agents/reviewer.toml` (one line each). A test requires `reviewresult.Parse` to accept the object that the delta spells out, filled with each value the delta lists, so the agent's instructions and the parser cannot drift apart. A reply with findings and no `id` is now refused by `Parse`; `odd/review-results/` holds no stored result.
- `labdrian review bind` and `labdrian review record` (own-rdd T2, S3, and S1 for the binding and the storage). `bind --base <rev> --head <rev> [--cwd <repo>]` resolves both revisions to full commit names and prints one JSON object: `base`, `head`, `diff_sha256`, `paths`, `worktree`, `worktree_created`, `diff_bytes`, `diff_limit_bytes`, `over_limit` and, over the limit, a `note`. `diff_sha256` is the sha256 of one fixed git command under one fixed environment, so that `record` and a later delivery check recompute the same digest: `git diff-tree -p -r --full-index --binary --no-renames --no-color --no-ext-diff --no-textconv --ignore-submodules=none -U3`, with `core.quotePath`, `diff.suppressBlankEmpty`, `core.attributesFile=/dev/null`, `--attr-source=<empty tree>` and `core.compression=0` pinned, run without any `GIT_*` variable and under `LC_ALL=C` (git 2.40 or later); the paths come from `git diff-tree -r --name-only -z --no-renames`, so a rename is a removal and a creation. `odd/review-results/README.md` has the exact command, why each part is there, and what is not pinned (`$GIT_DIR/info/attributes`, the zlib of the machine). `bind` makes the detached worktree `<repo-parent>/<repo-name>-worktrees/review-<head12>` (beside the main checkout, never inside the repository; git's hooks do not run), reuses one already at `head`, and refuses a path that is a worktree of another commit or is not one of this repository. A diff over 150000 bytes is bound all the same and says so (`over_limit`, `note`). `record --feature <name> --base <rev> --head <rev> [--result <file>|-] [--cwd <repo>]` recomputes the binding from git, never from the reply, holds the reply to it with `reviewresult.Parse`, and stores `{version, binding, reply}` as `odd/review-results/<feature>/<head12>-<n>.json`, atomically and never over an existing file, then prints the RoleHandoff skeleton for `labdrian roles append --stdin` (`payload_kind` `review-report`, evidence `review-diff` and `review-result`) with the members only the parent knows (`project_id`, `goal_id`, `chain_id`, `seq`, `prev_sha256`, `to_role`, `context.summary`) left empty, so that `roles validate` refuses it until they are filled. `--feature` is one safe path segment and a symbolic link on the way is refused, so no input names a path outside `odd/review-results/`. Exit 0 stored, 2 reply refused (nothing is written and the error names the rule), 1 usage error or any other failure. Two concurrent `bind` runs of one head both succeed, the second reusing the worktree the first made; concurrent `record` runs take distinct numbers, with a short bounded backoff between tries. Every git call has a default timeout of 5 minutes, and a git that gives no answer is reported as such, never as a taken path. On linux the results directory is walked and written through held directory descriptors (`openat` with `O_NOFOLLOW`), so a symbolic link swapped in mid-call cannot redirect the write; elsewhere the directories are re-checked after use and a change is refused (a swap between the last look and the link is not seen there). A result whose directory cannot be flushed after the link is reported as stored, with a warning on stderr not to record it again, and `record` exits 0; for that `engine/atomicfile` gains `ErrDirNotFlushed`, which an error of `Replace` or `Create` satisfies when only the flush of the directory failed (its message is unchanged). When stdout cannot be written, `bind` and `record` exit 1 and say what was already done (for `record`, where the result is stored). Four new packages, all in the architecture test: `review` (domain), `review/app` (application, with ports for git and for the results directory), `review/gitexec` and `review/fsstore` (adapters). `labdrian review <verb>` is forwarded to the engine unchanged, like `roles`; its help is in `engine/cmd/usage.go`, `bin/lib/usage.sh` and the README.
- `labdrian review verify` and the contract of what the `verifier` role returns (own-rdd T3, S4). `verify --feature <name> --stored <result> [--verdicts <file>|-] [--cwd <repo>]` holds the reply of the verifier to a stored result with `reviewverdict.Parse`: one verdict per finding id of the result, each `reproduced`, `not-reproduced` or `not-run` with its command, its output and its `base_result`. A reply that breaks a rule is refused at the first one, with an error that wraps one named value (`ErrUnparseable`, `ErrUnknownMember`, `ErrUnknownID`, `ErrDuplicateID`, `ErrUnanswered`, `ErrOutsideEnum`, `ErrMissingEvidence`), as exit 2 with nothing stored. `reviewverdict.Decide` is the one pure function that decides whether the review blocks: a BLOCKER or CRITICAL the diff caused and the verifier reproduced on head blocks, a check that did not run is `unverified` and never clear, a WARNING is fixed before delivery, and a SUGGESTION or a finding of the base is carried. The reply is stored beside the result as `<head12>-<n>.verifier.json` (`odd/review-results/README.md` said `.verifier.md`), atomically and never over a file, and stdout is the skeleton of the record with the `verifier-report` evidence and `to_role` filled. A candidate, the feature and its base, is corrected at most once: a verdict that blocks another head of a base whose review a stored verdict already blocked is refused with exit 1 and stores nothing, and the round is recorded by the stored verdict itself, with no counter beside it. A verdict that blocks is checked and stored under a lock of the directory of the feature (an exclusive `flock(2)` on linux; none elsewhere), so two `verify` calls at the same time on two heads of one base cannot both spend the round. The `Results` port of `review/app` gains `Read` and `Lock`, and `roles/verifier/body.md` now returns the verdict object (`gadu-generate` rewrote the three agent files of the verifier; a test requires `Parse` to accept the object its delta spells out). `review` with no verb, or with an unknown one, now lists `verify` in its error message.

A skill that used to pass `validate` without a record is now reported `APPROVAL_MISSING` until `skills approve` records it. The list of the 34 global skills that predate the lint budget stays, for the lint only: it still lets `approve` record those skills with `warning:` lines for the size and description findings, and exempts no skill from approval.

### Changed

- A stored review result is one file per launch that holds the binding and the reply (`{version, binding, reply}`), where `odd/review-results/README.md` said the file was the reply alone, and `diff_sha256` is the sha256 of the canonical diff of the two commits, not of `git diff base head`. A reader of a stored result takes the reviewed head from `binding.head` (the value `reply.candidate.head` has too). `skills/role-chain/SKILL.md` names `labdrian review bind` and `labdrian review record` for the parent's binding and storage duties, and says that `bind` makes the review worktree where it asked the parent to compute the digest and to add that worktree with git; the skill changed, so its approval record is `APPROVAL_STALE` until the owner reviews it and runs `labdrian skills approve --id role-chain`.
- The shaper, builder and delivery role agents follow two new overlay skills in place of gentle's SDD skills (C15). `odd-feature-doc` gives the format of the ODD feature document `odd/tasks/<feature>.md` (a header, `## Specs` that quote the user verbatim, `## Tasks` with one line per task, an append-only `## Log` whose `L1` is the user's request) and the part each role plays in it: the shaper writes the Specs and Tasks, the builder checks off its tasks and appends its evidence to the Log, and delivery closes the document in place with one final Log entry, with no copy, no move and no `diff -r`. `test-first` is the builder's RED -> GREEN -> REFACTOR rule in place of `sdd-apply/strict-tdd.md`: one RED test per rule of the spec, one test for each existing behavior the change touches, and one evidence table; it does not keep the separate triangulation step of `strict-tdd.md`. Both are global custom skills for Claude Code, Codex and Pi and need an owner approval record (`labdrian skills approve`). The role bodies cite them instead of the four planning artifacts, `apply-progress`, `strict-tdd.md` and the archive copy, and `gadu-generate` rewrote `agents/`, `pi/agents/` and `codex/agents/` for the three roles; the descriptions of the shaper and delivery agents now say what they do. The `role-chain` skill lists the `payload_kind` values `exploration`, `feature-doc`, `progress`, `review-report`, `verify-report` and `close-report` where it listed the names of the SDD artifacts; the engine accepts any non-blank kind, so a chain recorded with the old names stays valid.
- `skills approve` binds the approval to every file of the skill, not to `SKILL.md` alone (C24). The record is version 2, and its `sha256` is the SHA-256 of the lines `<sha256 hex of the file> <x or ->  <path>` (the format of `sha256sum` with one character added after the digest: `x` when the owner execute bit of the file is set, `-` when it is not), one per regular file of `skills/<id>/` at any depth except `skills/<id>/.approval.json`, with `<path>` relative to the skill directory, in slash form, sorted bytewise; to recompute it by hand (the README, under "What the approval digest covers", has the same recipe over several lines and the macOS one): `(cd skills/<id> && find . -type f ! -path ./.approval.json | sed 's|^\./||' | LC_ALL=C sort | while IFS= read -r f; do if [ -n "$(find "./$f" -perm -100)" ]; then m=x; else m=-; fi; echo "$(sha256sum < "$f" | cut -c1-64) $m  $f"; done | sha256sum)`. `approve`, `add` and `skills validate` compute it with one shared function. The owner execute bit is covered because setting it on an approved script changes what the approval lets run without changing a byte (owner decision of 2026-10-26 on review finding R1-digest-ignores-mode); the other permission bits are not, so a checkout under another umask leaves an approval holding. Changing, adding, removing or renaming any file of the skill after approval, or setting or clearing the owner execute bit of one (`chmod u+x`), makes it `APPROVAL_STALE`; a symbolic link, or any entry that is not a regular file or a directory, makes it `APPROVAL_UNVERIFIABLE` (the class `validate` already uses for a skill it cannot read), never silently skipped. A record of version 1, which covered `SKILL.md` alone, is `APPROVAL_STALE` and says so; approve the skill again to write version 2. Any other version stays `APPROVAL_MALFORMED`. The README, the usage text and the engine's help now say what the digest covers; this also closes the review suggestions R2-002 (the vendoring adaptation of `security-audit` is covered by the digest, companion files included) and R2-003 (what the `sha256` of a record hashes, in which order, and how to recompute it).
- `memory:procedural-skills`, when a workflow is created and in `runtime probe`, now reads the project's procedural skills lock through the same reader the session-start probe uses, behind a project-context port (C10c), instead of only checking that the file exists: a lock that is present but cannot be read or parsed is `unavailable` with `the procedural skills lock cannot be read: <reason>` (for example `parse project lock: unsupported version 2, want 1`), where it was `available`. A valid lock stays `available` and a missing one `unavailable`, with new detail wording, so the hash of a workflow event that records the new text differs from one that records the old.
- `longterm-mem doctor` runs a ninth check, `promoted-pages-eligible` (C10a, #293): a promoted page whose source observation sync no longer keeps current (not pinned and no curated `topic_key`) is reported with a new advisory status, `warn`, naming the page, the observation, the reason and the remedy (`longterm-mem promote --id N`, or pin the observation). A `warn` never fails the doctor: the exit code counts `FAIL` only. `--json` carries `"warn"` as a status value.
- `longterm-mem skills-stale` names the status of a candidate with no Engram record `unrecorded` (`status:unrecorded`), where it printed an empty `status:` (C10b).

- The guard contracts follow the role agents: the minimalism and oo-quality contracts apply to `shaper` and `builder`, and the anti-generic-design guard to `builder`; all three are stripped from the `reviewer` and `verifier`. The deleted `sdd-design`, `sdd-tasks` and `sdd-apply` agents leave their `applies_to_phases`, so a prompt launched under one of those names no longer receives a contract. The Pi gate (`labdrian-gate.ts`) acts on `shaper` and `builder` only, which also brings the minimalism contract to them in Pi, as it already reached them in Claude and OpenCode.
- `pipkg build`, and the Pi runtime's `install`, `update` and `rollback`, remove a symbolic link under `~/.pi/agent/agents` that points to `<package>/agents/<file>` when the package they just built no longer ships that file, and say so: `pipkg build: GADU.md link removed (the package no longer ships it).` Only a link whose target is exactly that path is removed; a file, or a link to any other path (gentle-ai's own `review-*`, `jd-*` and `gentle-ai-*` agents), is left as it is. `pipkg check` changes nothing. `runtime status --target pi` names such a link as stale. The retire runs right after the build, so a machine without `pi`, or a failed `pi install`, no longer keeps a link that points at nothing.
- Every hook command `install-hooks` writes now single-quotes the binary path when it holds a character the shell treats specially (a space, a quote, `$`), in `command -v` and in the call; a path of plain characters is written exactly as before, so an installed `settings.json` does not change (C7). The minimalism, anti-generic-design, sync-trigger, review-receipt and shaper-guard entries are now repaired on install like the projection and approve-guard ones: an entry of those families that differs from what this version writes is replaced instead of kept. An entry that names a longer binary name containing ours and carries a family token is taken for ours (as `uninstall-hooks` always took it) and replaced too.
- The warning that `apply` prints when the longterm-mem MCP install fails no longer says a later `apply` will not retry: the next `apply` runs the install again.
- The `SessionStart` hook of `projection hook` now asks which sources of the memory plan can be read (C23 M8) and adds, to the instructions block, one line for each that cannot: `- Do not read <source>: it is unavailable in this session (<reason>).` It runs `engram stats` and the longterm-mem binary (`longterm-mem status`), looks for a longterm-mem MCP entry in the Claude Code, OpenCode or Codex config, and reads the project's procedural skills lock, all at once and each within three seconds; a source that fails or does not answer is unavailable with the reason. The line only informs: the plan and the gate are unchanged, and the gate-task rewrite and `memory plan --instructions` still print the block without it.
- `memory:procedural-skills`, in the observations a workflow records when it is created and in `runtime probe`, is no longer always `unavailable` with "no presence check exists for procedural skills": it stats the procedural skills lock of the project (`unavailable` with "the procedural skills lock was not found" or "the project directory is unknown, so the procedural skills lock was not looked for", `available` when the file is there, not opened). The hash of a workflow event that records the new text differs from one that records the old.

- `install-hooks` (`engine merge-settings`, and `runtime install|update --target claude`) and `uninstall-hooks` follow a `settings.json` that is a symbolic link, the whole chain of links: they read and replace the file the link names, the link itself stays a link, the new file is staged beside the file it replaces, and the backup is written next to that file (`<file>.bak`). Before, `install-hooks` replaced the link with a plain file of its own (mode 0600) and left the file the link named as it was, which broke the link of a dotfile manager without saying so. A link that leads nowhere, or a loop of links, is refused for both verbs, exit 1, `settings: <path> is a symbolic link that cannot be followed (nothing was changed): <reason>`, and nothing is created or changed; before, `install-hooks` wrote a plain file in place of a dangling link and `uninstall-hooks` did nothing. Everything else about the file is as it was: the bytes written (keys sorted, two-space indentation), the mode of the new file (0600), the backup at `settings.json.bak` (written before the file is replaced and not when nothing changes; its mode and the way it is written changed, see the next entry), and the words of every other refusal, except that a directory that cannot be written into now reads `settings: create temp: atomicfile: create temporary file: open <dir>/.settings-<n>.json.tmp: <reason>` where it read `settings: create temp: open <dir>/.settings-<n>.json.tmp: <reason>`.
- The backup `settings.json.bak` that `install-hooks` and `uninstall-hooks` keep of the file they replace is written by `atomicfile` (the owner's decision of 2026-10-09): whole or not at all, at the mode of the file it keeps, and it is refused, exit 1 and nothing changed, when `settings.json.bak` is a symbolic link. Before, it was a copy written in place with mode 0644 less the umask, whatever the file's mode was: the backup of a 0600 `settings.json` (the mode the program writes) could be read by everyone, a crash or a full disk in the middle left a truncated backup and lost the previous good one, a read-only `.bak` stopped the write (`permission denied`; it is replaced now), and a `.bak` that was a link was written through, to wherever it pointed. A failure of the backup or the replace now reads `settings: replace <file>: <reason>` where it read `settings: backup to <file>.bak: ...` or `settings: rename temp to <file>: ...`. The backup needs a no-follow open, so it is made on Linux and macOS only; on another platform a write that would replace a file fails before it changes anything.
- `install-hooks` into a `settings.json` that holds the JSON value `null` no longer crashes with `panic: assignment to entry in nil map` (exit 2): it exits 1 with `settings: <path> contains invalid JSON (not modified): JSON null is not a settings object` and changes nothing. `uninstall-hooks` of such a file still does nothing and succeeds, and `runtime status --target claude` still says the file is not found.
- `runtime install --target opencode` (and `update`) refuses to install when any contract the plugin carries does not parse, the optional `skills/_shared/oo-quality-contract.md` included: it exits 1 with `partial — OpenCode prompt config could not be derived from the contracts: skills/_shared/oo-quality-contract.md: <the parse error>` and writes nothing. Before, a malformed `oo-quality-contract.md` was left out of the plugin's prompt config in silence and the install reported success, so the plugin shipped without its guard and nothing said why (the owner's decision of 2026-10-09, `R3-opencode-secondary-contract-silent-drop`). The message of every contract that cannot be used now begins with the file, `skills/_shared/minimalism-contract.md: ...`, and the sentence before it no longer says `minimalism-contract frontmatter`. `status`, with a plugin installed from a valid contract that has since become malformed, now says `OpenCode config missing or invalid: current prompt_config could not be derived: skills/_shared/oo-quality-contract.md: ...` (partial) where it said the prompt config was stale (restart required).
- Each git call that `pipkg build|check` and the Pi runtime's package build make stops after two minutes and is reported as a git that could not answer (`context deadline exceeded`); before, a stuck git kept the command waiting without end.
- The git that `pipkg build|check` and the Pi runtime's package build run no longer inherits the variables that locate a repository: `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_COMMON_DIR`, `GIT_NAMESPACE` and `GIT_PREFIX`. Everything else of the environment (`PATH`, `HOME`, `GIT_CONFIG_*`, the locale) is passed as before. Run from a git hook, or by a wrapper that sets them, `pipkg check` used to compare the package against the repository those variables named (or, when they named nothing, against the worktree, saying the overlay was not a repository) instead of the overlay's own; it now reads the overlay's own repository, as it does outside a hook.
- `pipkg build|check` and the Pi runtime's package build no longer take a git that could not answer for a git that answered no. A git that is stopped, killed by a signal or cannot be started for a reason other than not being installed now fails the command (`pipkg: git could not answer: ...` for the build, `pipkg: asking git: ...` for the check), where it built a package with no recorded commit or compared it with the worktree and said so only in the disclosure. A machine without git, and a git that exits with a status, are read as before: the tree is not under version control. A ref that starts with a dash, such as a `LABDRIAN_PI_DEPLOY_REF` of `--output=<file>`, is refused (`git ref "..." starts with "-" and would be read as an option`) and every ref now reaches git after `--end-of-options` (git 2.24 or newer).
- `pipkg build` and the Pi runtime's link of `agents/GADU.md` read a frontmatter with the reader the skills lint uses, so the three agree on where it is. For files that are well formed nothing changes. A file that starts with a byte-order mark is now accepted (it was refused as having no frontmatter); a key that is indented under another key is no longer taken for a top-level one (`metadata:` followed by an indented `name: x` used to satisfy the build's name check, and an indented `description:` the link's); a SKILL.md whose block is never closed is refused (`SKILL.md frontmatter is not terminated`) even when a `name:` came before the end; and a fence that is indented is not a fence. The words of the refusals are the same. `pipkg` asks git through a port now; the environment git sees and its deadline are the two entries above.
- `LABDRIAN_PI_BIN` is no longer read. It named the `pi` to run, but only the tests used it (it is in no script, document or release note of this repository); the Pi adapter now finds `pi` on the `PATH` through a `CommandRunner` port, and the tests hand it a fake one. `LABDRIAN_PI_SKIP_SUBAGENTS=1` (documented in the README) and `LABDRIAN_PI_DEPLOY_REF` keep their names and their effect; the program reads them once at start and hands them to the Pi adapter and to `pipkg check` as options.
- Every `pi` command the runtime runs (`pi install`, `pi remove`, the Subagents extension install) now stops after five minutes and is reported as failed, `context deadline exceeded`, where a command that never ended held `runtime install|uninstall --target pi` for good.
- A registry entry that names an `install.targets` value that is not a runtime is refused listing the runtimes in the order `runtime capabilities` lists them, `must be one of: claude, codex, pi, opencode`; it listed them as `claude, opencode, codex, pi`. The set is the same (the skills registry now validates against the one list of runtimes that `engine/capability` owns, and `skills add` still gives a new entry `claude`, `opencode` and `codex`); only the order of the words in the refusal changed.
- `runtime <action> --target pi --config-root <dir>` keeps the Pi package under `<dir>`, at `<dir>/pi/labdrian-pi`, the way `$STATE_DIR` does (`$STATE_DIR/pi/labdrian-pi`); `--config-root` was dropped for Pi, so `status`, `install`, `update` and `uninstall` always acted on `$STATE_DIR/pi/labdrian-pi` (`~/.labdrian-overlay/pi/labdrian-pi` without `$STATE_DIR`). The package is under the root and never the root itself, so `--target all --config-root <dir>`, which gives the same directory to Claude, Codex, OpenCode and Pi, does not make the Pi build or `pi remove` replace or delete the settings the other three keep there. Without `--config-root` nothing changes. (`longterm-mem register --target pi --config-root` is a different command and still names the built package directory.)
- The `skills` verbs that read their command line with the new strict parser (`list`, `status`, `lint`, `validate`, `add`, `remove`, `sync-manifest`, `approve`, `install`, `adopt`, `project-register`, `project-revise`, `project-retire` and `project-status`) refuse a flag they do not read, exit 1 with `skills <verb>: unknown flag "<flag>"` and read or write nothing; `list`, `status`, `validate`, `add`, `remove`, `sync-manifest`, `install` and `adopt` used to ignore it, `lint`, `approve` and the four project verbs already refused it. A command line that is refused is now refused before the overlay lock is asked for, where it used to wait for it. The flags the wrapper appends to every verb (`--registry`, `--manifest`, `--source-root`) are still accepted by all of them, a flag written with an equals sign (`--registry=path`) is an unknown flag, and `lint` no longer lets a second path through after an empty first one.
- The four project verbs (`project-register`, `project-revise`, `project-retire`, `project-status`) take an empty first word as their word, as `lint` does: `project-register "" <draft>` used to skip the empty word and read `<draft>`, and now refuses the second word, exit 1. A command line that lacks `--candidate`, the draft or the id is refused before the project lock is asked for, where it used to take the lock first.
- `skills install` and `skills adopt` name the project, when `--project-id` is not given, by the origin remote of its repository (read from `.git/config` without running git, following a linked worktree to its common directory), and only then by the name of the directory. A checkout whose origin is `github.com/acme/demo` is that project whatever its directory is called, also from a subdirectory or a linked worktree; before, it was the name of the directory. A registry that admits a skill to a project (`install.allowedProjects`) names it by its origin, e.g. `github.com/acme/demo`. A `.git` file that holds no `gitdir:` line, and a directory above the project that cannot be inspected, are refused (exit 1) naming the file or the directory, where the first used to fall back to the name of the directory; the second says to give `--project-id`. A `.git` file whose `gitdir:` (or the `commondir` of that directory) leads to a directory that is not a git directory, one with no `HEAD`, is refused too, naming the file and the directory and saying to give `--project-id`: a worktree or submodule that was moved or removed used to fall back to the name of the directory, and a pointer to any readable `config` was read.
- The skills registry reader dispatches on the file's `version`: a version it does not know is refused first, naming it. A key it does not know no longer refuses the file: it is left out and said on stderr, the verbs that only read go on with the rest, and `skills add` and `skills remove` refuse such a registry because writing it back would drop the key. A field that install, approval or projection depend on (`id`, `path`, `source`, `source.type`, `install`, `install.defaultScope`, `install.allowedProjects`, `install.targets`) is refused, naming the field and the line, when it is not in the shape the reader reads; before, a value on the line of `source`, `install` or a list was ignored without a word. A list item in quotes may hold a colon followed by a space (`- "acme: demo"`): it was taken for a mapping and the file refused; it is the value it says.
- Contract frontmatter lists must be inline lists, `[a, b]`. The shapes that were tolerated (no brackets, an unclosed bracket, text after the bracket, an empty value) are now refused with a message naming the key, and quoted items now match. The frontmatter is the lines between the first two lines that are `---` and nothing else (white space at the end of a line does not count): a `---` inside a value (`injection_point: "## a --- b"`), in a longer run of dashes or followed by text used to end the frontmatter there, and is now part of it; a document whose closing delimiter is not a whole line has no frontmatter.
- The approval record of a skill (`.approval.json`) and the project lock (`.labdrian/procedural-skills.lock.json`) are read strictly: a key that appears twice in any object, and bytes that are not UTF-8, are refused with the word `duplicate JSON object key` or `not valid UTF-8`. Before, the last value of a repeated key won and bad bytes were replaced in silence, so a record could say one thing to the program and another to a person reading the file. The records the program writes are unaffected, and none of the repository's own carries either.
- An error that named its source twice names it once: `roles append` told a store it could not use as `role chain store: append: role chain store: ...` and now says `role chain store: ...`, as `roles validate` and the chain loader do. A registry line over 65,536 bytes is refused as `line N is longer than the 65536 bytes a line of a registry may have`, where it said `skills: read error: bufio.Scanner: token too long`. `skills add` and `skills remove` over a registry with fields the reader leaves out refuse with the error alone, which says which fields: the `warning: registry fields left unread: ...` line that came before it and said the same is gone (the verbs that go on still print it); `pipkg build` and the Pi runtime's apply, install and update, which refuse such a registry, do the same, and `pipkg check` keeps its warning. `skills install` and `skills adopt` that admit a skill and are given no `--source-root` say `skills install requires --source-root <dir>, the skills tree to read the skills from`, where they said the skill's path escapes the source root; a registry that admits nothing is still told so, exit 0. `runtime status --target pi` over a package it cannot prove lists what is unproven once, in the message, where it listed the same entries again after `— reasons:`. The exit codes are unchanged.
- The skills registry file is read to at most 4 MiB (about four hundred times the registry of this repository): a larger file is a registry that cannot be read, `read <path>: more than 4194304 bytes, the most a registry may have`, exit 1, where the whole file was held in memory whatever its size.
- `pipkg build` resolves the destination with the same rule as the rest of the engine (`pathguard/fsresolve`), so the overlap check never decides on a path it could not follow: a destination whose existing ancestry holds a symlink with no target, a loop of links, or a directory that cannot be read is refused before anything is built, `pipkg: resolving destination: ...`, where the overlap check used to read such a link as absent and the build did all its work in a temporary directory and failed at its last step (`creating ...: file exists`, or `swapping built package into place: ... not a directory`). The exit code and what is left on disk are the same; a destination that does not exist and is reached through no such link is built as before.
- `skills project-retire`, when it fails and rolls back, restores the project lock at the mode the lock has when the retirement commits, as `project-register` does, and no longer at the mode it had when the retirement was planned; the two differ only if the lock's mode was changed in between.
- A workflow created from now on is recorded in a new version of the workflow log: version 2. Its created event also holds `profile_snapshot`, the whole profile as the catalog gave it when the workflow was created (its name, stages, roles, checks, the three policies, the memory default and the review dependency), and `profile_digest`, the SHA-256 in lowercase hex of the snapshot's compact JSON; every later event of the log is of version 2 too and holds neither. A workflow goes on from that snapshot: `workflow stage`, `workflow verify`, the projected context and the memory gate use the profile in the log and no longer ask the built-in catalog, so a workflow does not change, and does not stop, when a built-in profile is edited or retired. A workflow whose log is of version 1 (every workflow created before this change) is read, continued and closed exactly as before, by name, and its log stays version 1 from end to end: no version 2 event is ever appended to it. Nothing that `workflow create|start|pause|resume|stage|verify|close|status|bind|unbind` or the hooks print changes (the goldens recorded before the change pass unchanged); what changes is the bytes of the log of a new workflow. A program from before this change reads a version 2 log as one that is not its own (`classification: foreign`) and refuses to append to it, so a workflow created by this version is not to be carried on by an older one. `workflow status` of a version 2 workflow whose recorded profile is no longer the built-in profile of its name gains an optional `profile_drift` object (`kind` `changed` or `retired`, `profile`, `recorded_digest`, and for `changed` the `current_digest` and the differing `fields`); `workflow verify` of such a workflow prints one warning line on stderr naming the drift and still succeeds, exit 0, with the same stdout as before. Without drift the field and the line are absent, so every status and verify printed before keeps its bytes; a version 1 workflow never reports drift; no other verb and no hook mentions it, and nothing is refused: if the check itself fails (the catalog errors for a reason other than having no such profile), `workflow status` still prints the state it always printed and `workflow verify` still succeeds, each with one stderr warning, `could not check whether the profile drifted`, and the exit code is unchanged.
