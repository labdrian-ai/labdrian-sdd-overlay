## 2. Value evidence (Q2)

**Receipts.** 110 review-state files, all terminal `approved`; risk 20 high / 38 medium / 52 low; 52 ran no lens (passive), 30 one, 2 two, 5 three, 21 four. Lens launches: reliability 58, risk 28, readability 24, resilience 23 (133). Findings 194: reliability 110, readability 51, resilience 26, risk 7. Severe (BLOCKER/CRITICAL) 13: reliability 8 (2 BLOCKER), resilience 3, readability 1, risk 1 (inferential, pre-existing → `info`). Per launch: findings 1.9 / 2.1 / 1.1 / 0.25 (reliability / readability / resilience / risk); candidate-caused severe 0.14 / 0.04 / 0.13 / 0.00. 7 of the 58 lens-running reviews found a blocker; 7 of 110 lineages carried a correction delta; 3 reached generation 2. 62 findings sit in `_test.go` files and 78 in `.md` files (72% about tests or docs). Cross-lens duplication: 21 same-file groups reported by more than one lens inside one receipt; `runtime-adapters.md:111` lists 4 duplicate pairs among RA3-B's 11 findings and `:115` 2 more.
**Ledger.** "fix round" appears 115 times in Phase 9; each round is a new lineage over the fix commit (batch 18: 4 extra rounds, ≈1.5 h, no product defect — memory `resolve-every-review-finding`). `lens_context_budget_exceeded` 8 times (`:136,446,461`), threshold between 170 and 189 KB of diff (`runtime-adapters.md:107`): a 30-file commit was rewritten into nine (`phase9:446`), a 476 KB data file into eleven commits (`:461`), and split artifacts became findings (`runtime-adapters.md:109`: `R2-unbindifunchanged-no-caller`, `R3-unbind-cas-unwired`). Context blindness on record: `phase9:138, :207, :320` ("which the reviewer of that diff could not see"), `:477` ("the reviewer saw only the data"), `:706`, `skill-lifecycle.md:84` ("outside the diff hunks the reviewer saw"), `runtime-adapters.md:119`.
**Judgment-day (the polisher's protocol, same findings schema).** union-retrieval round 1: 3 severe, 1 found by both blind judges, 2 by one judge each and verified by the orchestrator (`ledger-round1.md:7-68`); round 2: all 3 proven load-bearing by mutation, 2 new single-judge warnings, 1 measured harmless (`ledger-round2.md:21-66`); PR-5: 1 CRITICAL by both, 4 WARNING (3 single-judge, 1 verified by mutation), all `introduced` (`ledger-pr5-round1.md:17-76`). A second blind launch of the *same* scope added recall (5 of 8 true findings came from one judge only); a second *lens* mostly added duplicates (the 21 groups above).
**Cost.** Context re-read dominates (24B context vs 80M output tokens, 97.6% cached; `docs/architecture/adr-telemetry-cost-baseline.md:9-12`). Every lens launch re-reads the candidate plus its 1,116-word file: a four-lens review of the sample candidate `HEAD~4..HEAD` (62,763 B ≈ 16k tokens) costs ≈63k candidate tokens plus ≈4 × 1.5-2.2k of agent text, 60% of it the dead block; at the 150 KB planning cap (`runtime-adapters.md:107`) ≈150k. One launch of a 443-word-class file costs about a quarter.
**Conclusions.** (1) One parametrised `reviewer.md`; the lens is a prompt row. (2) Default = one launch whose scope is reliability + resilience (behavior and failure paths; 11 of the 12 true blockers), with the acceptance criteria inlined. (3) Readability as a second row only when the unit changes docs, public API, messages or help text (1 CRITICAL in 24 launches, 78 findings in `.md` files). (4) Risk never earns its own launch here: 0 candidate-caused severe findings in 28 launches, both safeguard refusals hit it (§5); its checklist (secrets, permissions, path escapes, exec/net imports) is one line in every launch, and Task Size item 2 routes to deterministic checks the repo already has (`runtime:TestPhase7PackagesImportNoExecOrNetwork`, `skills:TestZeroFetchImportAllowlist`). (5) For a unit whose Risk line names a high-risk item, a second blind launch of the same scope with another model (per-launch `model`, §6) instead of four lenses. (6) No refuter call: the verifier reproduces each severe finding (named test, compile, run, or the fix reverted in a `mktemp -d` copy) and settles `unknown` causality against `base`.

## 3. Independence without gentle's provider (Q3)

| Option | No mutation | No drift from the frozen candidate | No live-worktree reads | Enforced by harness vs prose |
|---|---|---|---|---|
| (a) parent inlines `git diff base head` in the prompt | `tools: Read, Grep, Glob` cannot write | the bytes are in the prompt; `diff_sha256` names them | tools-less variant absolute; with Read tools: prose only | harness: tools, digest; prose: nothing else to ask; weakness: context blindness (7 recorded errors) and the size budget |
| (b) detached worktree at `head` under `~/labdrian-sdd-overlay-worktrees/`, `tools: Read, Grep, Glob` | same allowlist; `git worktree add --detach` leaves the index untouched | detached HEAD at the exact SHA; nobody edits it; removed after the verdict | `Read` accepts any absolute path → prose + the parent's spot check of cited `path:line` against `git show head:path` | harness: tools, SHA; prose: "read only under this path" |
| (c) `Bash` with read-only git | Bash is not read-only by construction; `permissionMode: plan` is ignored when the parent runs in `acceptEdits`/`bypassPermissions` (docs) | only if the agent uses `git show head:` — prose | prose | prose everywhere → rejected |

**Recommendation: (a)+(b).** The inline diff *is* the candidate (identity: full `base` and `head` SHAs of a committed range, `diff_sha256 = sha256(git diff base head)`, ≤150 KB per launch per the ledger's planning rule, else one launch per commit — never a truncated diff); the detached worktree is read-only *context* so the reviewer can check an unchanged helper before calling it undefined. Native `isolation: worktree` is unusable for this: it branches from the default branch (or local `HEAD` with `worktree.baseRef: "head"`), never from a given SHA, and lives under `.claude/worktrees/` inside the repository (Claude Code worktrees doc, read 2026-10-22), which the stop-hook incident forbids (memory `no-worktrees-under-scratchpad`). The parent therefore runs `git worktree add --detach ~/labdrian-sdd-overlay-worktrees/review-<head12> <head>` (rung 2) and `git worktree remove` after the verdict — the owner already does the first half: `git worktree list` shows 36 clean `bNN-review` worktrees, each `(detached HEAD)` at a candidate commit, never removed (a Phase 9 cleanup item). Binding of the verdict: the reviewer echoes `candidate{base, head, diff_sha256}`; the parent refuses a result whose echo differs from what it sent, stores the JSON as a file, and appends the handoff with `evidence[] = [{kind:"review-diff", ref:"<base>..<head>", sha256:<diff_sha256>}, {kind:"review-result", ref:<file>, sha256:<file digest>}]`; delivery recomputes `sha256(git diff base head)` and trusts the record only on equality. Different bytes → different digest → the record does not apply. Context files the reviewer cites are checked by the parent for every severe finding (`git show head:path`), which the reproduction step needs anyway.

## 4. Output and verdict (Q4)

Result (the sub-agent's whole final text, one JSON object; this is the one core-prefix line the reviewer and polisher deltas override, as v2 already did for the polisher): `{"candidate":{"base":"<sha>","head":"<sha>","diff_sha256":"<hex>"},"inspection":{"status":"completed|incomplete","paths":["<every changed path inspected>"],"reason":"<why incomplete, else empty>"},"findings":[{"id":"<stable id, unique in the result>","location":"path:line|path:start-end","severity":"BLOCKER|CRITICAL|WARNING|SUGGESTION","claim":"...","evidence_class":"deterministic|inferential","causal_disposition":"introduced|behavior-activated|worsened|pre-existing|base-only|unknown","proof_refs":["..."]}],"evidence":["what was inspected"]}`. Clean = `"findings":[]`. No `schema`, lineage, receipt, authority or `GENTLE_AI_*` field ever: a labdrian review is check evidence in the role chain, never review authority (`docs/architecture/standalone-product-roadmap.md:93`).
**Mapping onto `RoleHandoff`.** `payload_kind: "review-report"` (same convention as `verify-report`, `sdd-phase-common.md:53`), `payload_sha256` = digest of the stored result file, `evidence[]` as in §3 plus `{kind:"verifier-report", ref, sha256}` when the verifier ran; `context.summary` = counts by severity and the verdict; `context.open_questions` = findings that need a product decision. `status: completed` only with a validated result; a refused launch, a model refusal, an unparseable result, an echo mismatch or `inspection.status: incomplete` → `status: interrupted`, `resume_reason: "review not run: <reason>"` (`handoff.go:30-34`), which the chain re-runs; nothing is ever recorded as approved by absence (`roadmap.md:93`).
**Who decides.** The reviewer returns findings; the parent synthesizes, as judgment-day's orchestrator does (`ledger-round1.md:29-33`). A severe finding counts only when `causal_disposition` is introduced / activated / worsened *and* the verifier (or the parent inline within its 3-call budget) reproduced it; `unknown` goes to the verifier against `base` first. Reproduced severe → `reviewer → builder` (the chain's only backward transition, `roles.go:138`) with the result file as the builder's ledger; WARNING → fixed before delivery and SUGGESTION → carried to the next unit, per the owner's rule (memory `resolve-every-review-finding`); clean or carried-only → `reviewer → delivery`. Delivery is blocked by: a reproduced severe finding, an incomplete or not-run review, or a digest mismatch at delivery time. The delivery role finds this out by running `labdrian review check --feature <feature>` for the head it delivers (own-rdd T4, S5): the check recomputes the digest from git and refuses with exit 1 on each of those and on a severe finding no verifier checked, and the role then closes nothing and returns `blocked`. The parent never launches a correction loop: one fix unit, one new review of the fix commit, as the ledger already does.

## 5. Model and safeguard (Q5)

Facts (memory `reviewer-lens-safeguard-refusals`, `~/bin/claude:2-9`): gentle's lenses run through `claude --print` with no `--model`, so the wrapper picks it; Fable 5.1 refused the resilience/reliability lens context on 2026-09-10, Opus 5 refused it on 2026-09-20 (path-traversal and symlink-escape test fixtures in the candidate), Sonnet 5 ran it but on 2026-10-06 twice reported the risk-lens candidate uninspectable while claiming completion, and Sonnet 5.5 ran the same lens cleanly, so the wrapper now forces `claude-sonnet-5-5` for `--print`. Implications: (1) the refusals were triggered by candidate *content* handed to a tool-less model as a wall of patches; wording cannot remove them, so the reviewer prompt stays neutral ("inspect", "report defects", gentle's "neutral claim") and the refuter's "attack each claim" framing goes with the refuter. (2) Our reviewer is launched by the `Agent` tool, not `--print`, so the wrapper never applies; the model comes from the agent file: `model: sonnet` (the owner's rule "ese lente siempre tiene que ir usando sonnet"; every Phase 9 receipt, the 12 corroborated blockers included, was produced under the wrapper's Sonnet 5 / 5.5 default — inferred from the wrapper dates, not recorded in the receipts). (3) Claude Code resolves the per-invocation `model` parameter above the frontmatter (docs, v2.1.251+), and the engine's hook already echoes that field (`engine/hookwire/encode_test.go:119-127`): on a safeguard refusal or an incomplete inspection the parent relaunches once with another model via `model`, and if that fails too records "not run"; never a declared "reviewed". (4) Alias versus pinned id is an open decision (§10): `sonnet` follows the latest Sonnet (which once regressed), `claude-sonnet-5-5` pins a known-good one and goes stale.

## 8. External practice (only what changed the design)

- Claude Code Review product doc (code.claude.com/docs/en/code-review, read 2026-10-22, page undated; verified in source): "several agents examine the diff and the surrounding code in parallel", then "a verification step checks the candidate findings against the code and filters out false positives", then dedupe and rank; "A review never approves or blocks the pull request"; it reads "without building or running your code". Taken: surrounding code (the worktree), a verification pass before a finding counts (the verifier), the parent/owner decide. Not taken: no execution — our verifier runs the checks because the ledger's refutations were compiles and test runs.
- Qiu & Gill, "Adversarial Review: Structured Disagreement for Grounded Agentic Code Review", arXiv:2608.18167, submitted 2026-08-16 (abstract read; results tables not read): a critic "audits the review through structured disagreement", "outperforming a five-agent baseline while using only three agents", and names a "false-consensus failure mode, where agents converge on agreement without sufficient evidence". Taken: fewer launches plus an evidence-grounded refutation of each finding — ours deterministic, not a second model.
- Cihan et al., "Evaluating Large Language Models for Code Review", arXiv:2505.20206, 2025-05-26 (abstract read): GPT-4o and Gemini 2.0 Flash judged correctness right 68.50% and 63.89% of the time *with* the problem description, worse without. Taken: inline the acceptance criteria (`S#`) in every launch; no model verdict blocks without reproduction. Secondary write-ups quoting ≈25% wrong suggestions on correct code were not verified in source and are not relied on.
